What happens to agent code after it merges

Five papers from March to September 2026, each read in full by its own agent. The question they share is the one wf lives with: every round builds on code an earlier agent wrote. Does that code hold up, and does wf catch the ways it doesn't?

Per-paper notes: docs/research/papers/<id>.md. The papers' findings are in the notes with section and table numbers. Everything about wf on this page is inference.

The short answer

Agent code passes its tests and still gets worse to build on. The decay shows up in edge behaviour and in structure, not in the tests. Telling the agent to write better code doesn't stop it. wf already does the things the papers point to: small, bounded steps, a check after every commit, and behaviour verified before and after. Two gaps remain. A round never runs JewelryX's full test suites, and nothing measures what happens to a round's code after it merges.

Where they agree

all five

Green tests don't mean healthy code

  • CodeThread: every drifted PR passed every existing test.
  • SlopCodeBench: functionality pass rates barely moved (63% → 58%) while erosion climbed.
  • SWE-CI: lint ranks agents above humans, the Maintainability Index ranks them below.
  • RoadmapBench: strong models fail by writing code that builds but is wrong.
CodeThread · SlopCodeBench

The next agent copies what it finds

  • Contract drift survives the next PR in 86% of cases. In one TypeScript example, the next agent copied a wrong disabled guard onto a new option.
  • Duplicated code grew 96%, while new rule violations grew 0.3%.
That's measured evidence for your principle that "the codebase teaches the next change".
CodeThread · SlopCodeBench

Edge behaviour breaks first

  • CodeThread: the only code-level cause found was a changed guard, default, or exception.
  • SlopCodeBench: error-handling tests fell fastest (80% → 62%), while functionality held.
Neither paper cites the other; linking them is my synthesis.
CodeThread · SlopCodeBench

Instructions don't hold the line

  • SlopCodeBench: the anti-slop prompt kept the slope the same, lost 2.4 pts of correctness and cost 12% more.
  • CodeThread: PR1's prompt spelled out the exceptions and edge cases, and agents drifted on exactly those.
That backs "verification beats instruction".
four of five

Size is the risk

  • RoadmapBench: success falls with each extra target, down to 15% at seven or more.
  • CodeThread: extra lines in the follow-on PR go with failure (OR 1.88).
  • SlopCodeBench: plain line count predicts the next step better than the paper's own erosion score.
  • 2609.17598: the largest PRs come with the worst signals.
SWE-CI · RoadmapBench

Breakage spreads unless checked at each step

  • SWE-CI: regressions are common, and become more frequent in later iterations for 12 of 20 models.
  • RoadmapBench: one broken import takes down everything built on it.

Where they disagree: measure complexity or not?

For measuring it

SlopCodeBench and SWE-CI both show agent code is structurally worse than human code: 2.0× more erosion, and 0 of 20 models beat humans on the Maintainability Index. Their readers suggested a complexity ratchet in wf check.

Against gating on it

In CodeThread, complexity, Halstead volume and line count at PR1 predict nothing about the next agent's success (OR ≈ 1.0, p ≥ .78). SlopCodeBench's own data agrees: its erosion score doesn't predict the next checkpoint passing (−0.018).
How I'd settle it: complexity rises, but nobody has shown it causes the next failure. Contract drift has been shown to, and it survives. So a contract change gets a check, and complexity gets a number shown at T2, not a gate. That keeps wf from growing machinery the evidence doesn't pay for.

What to do, cheapest first

Your pay-as-you-go rule still applies: these papers are other people's rounds. So the first step measures whether any of this shows up in yours.

1 · Count rework on the rounds already merged measure

JewelryX already has 78 round folders in bug-reports/. For each merged round, count the follow-up fix commits and reverts that touch its files within 30 and 90 days. Compare that with your own commits from before wf, in the same repo. This is 2609.17598's method on your data. It also answers "is wf paying off", which we found earlier has no answer today.
Cost: one script, run on demand, never a gate. Match each round to its merge commit, not by message (the paper's own weak spot).

2 · Run the full suites before T2 gate

Once validate is done, run the backend pytest suite and both vitest suites against the worktree. Fail if any test that passed at the round's base now fails, or has been deleted or skipped. That's SWE-CI's "compare against the base" step. Today a regression in a test the round didn't touch is first caught at the qa gate, after merge, when it's no longer the round's to fix.
Cost: about 35–45 s per vitest suite plus the Mongo-backed backend suite, once per round rather than per commit. It belongs in projects/jewelryx/checks.ts.

3 · A contract-change list at T2 rule

One wf standards rule, written as a .agents/checks/ file in JewelryX (the project owns it, not wf). For each touched function it lists added or removed guards, silent defaults (.get(k, default), ?? x, Pydantic defaults), changed exceptions or HTTP statuses, and a changed return shape. Each line reads "X now rejects / accepts / defaults Y". It goes next to the diff at T2. An intended change needs a test that pins it; an unintended one is reverted before T2. If the same pattern is flagged twice, it becomes a lint rule.
Evidence: CodeThread's strongest effect, and SlopCodeBench's fastest-decaying tests. Cost: a markdown file, no wf code.

4 · Two numbers on the T2 page show, don't gate

The lines changed per commit and per round, and complexity before and after for the touched functions (ruff C901 / ESLint complexity). Shown, not enforced, and dropped if they never change a T2 decision.

Not to do

  • Complexity or Maintainability Index gates. They predicted nothing in CodeThread, and SlopCodeBench's own score didn't predict failure either.
  • More prompt rules about clean code. SlopCodeBench shows the slope doesn't move, and correctness drops.
  • Choosing models from these rankings. They're snapshots that change within months, and in 2609.17598 the product, its users and the tasks are mixed together. Measure a model change on your own rounds.
One rule to revisit: "touch only what you must" is right for the diff's reach, but SlopCodeBench's failure mode is a minimal diff that adds a fourth branch to an already complex function. A plan line at T1 saying where new logic goes ("extends X" or "new function, because…") would surface the choice while it's still cheap to change.

How far to trust it

  • None of the setups had a human gate. No plan approval, no diff review, and in two papers the agents couldn't even run tests. wf has all of these, so the effect sizes are upper bounds for wf, and the directions are what carry over.
  • Almost everything is a single run, with few or no significance tests. Several papers' numbers disagree between sections; the notes list them.
  • They're mostly about Python libraries. Nothing covers SvelteKit UIs, MongoDB state, or screenshots.
  • Their task sizes differ from wf's. RoadmapBench's tasks are about 3,700 lines and SlopCodeBench's steps are whole features. wf's rounds are mostly small fixes, the easiest class in both papers that split by task type (CodeThread −4 pts on bug fixes; RoadmapBench 64% vs 36% for new components).
  • Compounding over many rounds is untested. CodeThread's chains have only 2 steps, and wf's real exposure is dozens of rounds on top of each other. Its 86% persistence suggests things get worse over that, but no paper measures it. Step 1 above would.

Questions for you

  • Should step 1 run now, on the 78 rounds? It's the only step that tells us whether any of this happens in JewelryX.
  • Is a few minutes per round worth a full-suite run before T2, or should it run only on rounds that touch the backend or a shared package?
  • Does the contract-change list belong at T2, or earlier, as something the commit agent has to justify?
