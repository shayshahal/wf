## 2. Question
Can current frontier coding agents do long-horizon, multi-target development on an existing codebase,
meaning a whole release's worth of features (median ~3,700 LOC across 51 files), rather than the 33–107
LOC single-issue fixes in SWE-bench? Where do they stall, and does partial-credit scoring show what
pass/fail hides? The paper is mainly a benchmark contribution plus a diagnostic analysis of failures.

## 3. Method
**Task.** The agent starts in a Docker image of a repo pinned at release N. Git history is kept, but
branches and tags after N are pruned and upstream access is blocked. It gets `instruction.md`, a
"roadmap" with a median of 5 targets (range 3–12). Each target says *what* to build (API signatures,
parameter semantics, defaults, exceptions) and withholds *how*. The job is to implement release N+1's
behaviour. The agent sees no target code, tests, or oracle patch. Appendix F gives a full example
(Optuna 3.6→4.0: 5 targets, oracle 164 files and 7,794 LOC).

**Dataset.** 115 tasks, 17 repos, 5 languages. Python: Polars 13, PyG 10, Optuna 8, spaCy 5, Falcon 5.
TypeScript: MikroORM 10, Prisma 9, Valibot 3. C++: Glaze 14, thread-pool 6. Go: Fiber 6, Kitex 6,
Fyne 5. Rust: Ratatui 6, Diesel 3, Slint 3, Ruff 3. Domains: ML & Data 36, Web & RPC 17,
ORM & Validation 25, Infra & Tooling 23, UI & Rendering 14. Oracle patches run from <300 to >30,000
lines (median 3,714 lines, 51 files). Releases span 2017–2026 and repos range from ~20 KB to ~10 MB
(Table 3, App. E). The repos do not overlap with existing benchmarks.

**Construction pipeline (§3.3, App. G).**
1. Mining: repos with ≥1,000 stars, ≥5 tagged releases, still releasing in 2025, and at least 3
   high-quality natural-language release notes. Experts then pick consecutive version pairs with a code
   delta of ≥500 lines, at least one externally visible behaviour change that a deterministic test can
   express, and notes detailed enough to write an instruction from.
2. Construction: they align the diff with the release narrative to write the roadmap. Tests are
   adapted from upstream suites. A gold patch is extracted and refined until it passes them.
3. Static validation, by expert reviewers assisted by Claude-Opus-4.7:
   - A 20-item compliance checklist covering: spec clarity; implementation leakage (algorithm steps,
     internal names, pseudo-code, disclosing a bug's root cause, refactoring checklists); information
     integrity (no test names, no version or repo names); narrative quality; and test conventions
     (deterministic, environment-independent, no checks of internals beyond the public contract,
     weights sum to 1).
   - A per-target instruction–test alignment review on four axes: **completeness** (every behaviour a
     test asserts is stated in the instruction), **faithfulness** (tests assert nothing beyond the
     spec), **fairness** (no unstated assumptions such as exact error wording or internal names) and
     **minimality** (drop dead-letter matching tests).
4. Rollout QC: agents from three capability tiers attempt each task. Two annotators classify each
   failure as task-side (T: instruction gap, brittle test, environment, grading error) or model-side
   (M: design failure, implementation bug, debugging failure). On 40 trajectories Cohen's κ was 0.83.
   T-defects are fixed and the task is re-run. A task is finalised only when it has no T-defects, the
   oracle scores 1.0, and the model tiers get distinguishable scores.

**Models (13).** Claude-Opus-4.7, Claude-Opus-4.6, GPT-5.4, Gemini-3.1-Pro, DeepSeek-V4-Pro, GLM-5.1,
Kimi-K2.6, Mimo-V2.5-Pro, Qwen3.6-Plus, Kimi-K2.5, MiniMax-M2.7, Qwen3.5-397B, Seed-2.0-Pro.
Extended thinking is on for all. Reasoning effort is "high" for GPT-5.4, Gemini-3.1-Pro,
DeepSeek-V4-Pro and Seed-2.0-Pro, "xhigh" for Claude-Opus-4.7, and default for the rest.

**Scaffolds.** OpenHands is the primary scaffold for all 13 models. As an ablation, 11 models also ran
on Terminus 2, Harbor's reference agent (GPT-5.4 and Gemini were not run on it). Budget is 2 hours of
wall-clock per task. **There is a single trial per model**, and no seeds or variance are reported for the
main table.

**Metrics (§4.1).** Each subtask j of task i has a weight w_ij "reflecting its relative complexity" and
a binary pass/fail. How the weights are set is not specified beyond that.
- Per-task reward: r_i = Σ w_ij·pass_ij / Σ w_ij.
- **Resolved rate:** the fraction of tasks with every subtask passing.
- **Completion Score:** the mean of r_i over tasks.
- Also reported: average turns and output tokens (K) per task.

**Failure analysis (§5.6, App. H).** Claude-Sonnet-4.6, run agentically in Claude Code, classified 3,603
failed subtasks (1,065 task groups) into 5 categories and 14 sub-types. On 50 hand-checked samples it
agreed with expert labels 88% of the time at category level. Cost was about $350.

**Baselines.** No human baseline. The only comparisons are to other benchmarks: the same models are said
to score "80%+" on SWE-bench Verified.

- **Terminus 2 results** (Table 2): Opus-4.7 38.3 / 0.681 (59.2 turns), Opus-4.6 31.3 / 0.666,

- **Partial progress is the norm** (§4.2). Completion Score is always well above resolved rate: for
  Opus-4.6, 0.627 vs 32.2%. GPT-5.4 is notable: it resolves 29.6% but gets only 0.497 completion, a
  lower ratio than Opus. The authors read this as agents "stall on later targets, integration, or
  correctness".
- **Domains** (Table 2):
  - ML & Data is hardest. Six of 13 models resolve 0, and only the top 3 exceed 8% (Opus-4.7 30.6%).
  - UI & Rendering separates the tiers most: Opus-4.7 64.3%, Opus-4.6 57.1%.
  - ORM & Validation is "relatively more tractable", which the authors explain as structured
    schema/validation APIs.
- **Steps and compute (§5.1, Fig. 5).**
  - Fleet means are 134 steps and 18% resolved.
  - Opus-4.7 and GLM-5.1 use similar budgets (140 vs 163 steps) but differ by more than 20 pp.
  - Most models saturate within about 200 steps. Opus-4.7 is "the main exception" and keeps improving
    past 200.
  - DeepSeek-V4-Pro plateaus earlier than GLM-5.1 at a similar final rate.
  - Seed-2.0-Pro is a low-compute, low-performance outlier, read as premature termination.
- **Tool allocation (§5.2, Fig. 6).**
  - Opus-4.7 has the best result with about 101–102 tool calls per task and the lowest Explore share
    (35%).
  - GLM-5.1 and Kimi-K2.6 make more calls and spend more than half of them exploring.
  - GPT-5.4 averages 163 calls; Seed-2.0-Pro averages 36.
  - Explicit Plan and Think tool calls are sparse for most models.
  - Conclusion: allocation, not volume, characterises success.
- **Complexity (§5.3, Fig. 7, 95% Wilson CIs).** Resolved rate falls monotonically with files changed,
  lines changed and number of targets.
  - Files: Claude falls from 48% to 19% across the range, Gemini from 43% to 8%.
  - Lines: Claude and Gemini both start near 41% under 1K lines. Both converge "near the floor" above
    10K lines.
  - Targets: at 7 or more, Kimi-K2.5 resolves 0% and Claude 15%. Target count is the sharpest
    discriminator of the three.
- **Scaffold sensitivity (§5.4).**
  - Top models are robust: Opus-4.6 moves 0.9 pp between scaffolds, while mid and low tiers swing
    3–10 pp.
  - OpenHands is better for most models (DeepSeek-V4-Pro +7.9 pp, MiniMax +6.1 pp). The authors credit
    its typed tool schemas.
  - Terminus 2 is better for GLM-5.1 (+2.6 pp) and Qwen3.6-Plus (+4.3 pp), credited to its batched JSON
    commands per turn.
  - Opus-4.7 gets almost the same score on Terminus 2 with 59 turns instead of 140.
- **Target-level (§5.5, Fig. 8).**
  - Mean subtask pass rate rises from **36% for Component Creation to 64% for Bug Fix**. In between
    are Feature Addition, Feature Enhancement and Behaviour Change; their numbers are in the figure only.
  - On Component Creation and Feature Addition, Claude stays above 50% while Seed drops below 25%.
  - On Hard subtasks: Claude 53%, DeepSeek 43%, Seed 16%.
- **Failure modes (§5.6, Table 5–6, n=3,603).** The overall mix:

  |---|---|---|
  | Implementation Error | 38.5% | Code Defect 23.1%, Wiring Error 6.8%, Misunderstanding 5.9%, Edge Case 1.4%, Runtime Crash 1.4% |
  | Build Error | 28.3% | **Cascading 15.8%**, Syntax/type 11.1%, Dependency 1.4% |
  | Missing Implementation | 22.6% | Not Implemented 13.8%, Partially Implemented 8.8% |
  | Interface Mismatch | 6.5% | Wrong Signature 3.7%, Wrong Path/missing re-export 2.7% |
  | Agent Failure | 4.0% | Abandoned 3.5%, Exhausted 0.5% |

- **Failure modes by tier** (Table 6, App. H.4). The pattern shifts with capability:

  | Model (subtask pass rate) | Main failure | Other failures |
  |---|---|---|
  | Opus-4.7 (70%) | Implementation 55% (Code Defect 38%) | Build 4%, Missing 29%, Agent 10% |
  | Opus-4.6 (64%) | Implementation 58% | Build 15% |
  | GPT-5.4 (55%) | Missing 36%, the highest of any model | Agent 9%, all "Abandoned" ("analysis paralysis") |
  | Gemini (45%) | Build 38% (cascading 22% of failures) | Implementation 33% |
  | Seed (17%) | Build 41%, Missing 31% | Implementation 17% |

- **Spec quality had a large effect (App. G.3.3, Table 4, Terminus).** 45 of 115 tasks (39%) needed at
  least one fix round for task-side defects, averaging 3.1 rounds. Fixing them changed scores as follows:

  | Model | Resolved % before → after | Completion before → after |
  |---|---|---|
  | Opus-4.6 | 19.1 → 30.4 (+11.2 pp) | 0.564 → 0.683 |
  | GLM-5.1 | 17.4 → 20.4 (+3.0 pp) | not stated |
  | Kimi-K2.5 | 6.1 → 7.1 (+1.0 pp) | not stated |

  So the strongest model gained most from clearer specs and tests.
- **Case studies (App. H.5).** Each illustrates one failure category:
  - Code Defect: Kimi-K2.5 passes 6 of 7 tests; one `/` instead of `*` in a Gini normalisation gives
    0.125 instead of 0.5.
  - Cascading build error: GPT-5.4 writes one absolute import that creates a circular import in
    Falcon, so 0 tests collect and all 5 subtasks fail.
  - Missing implementation: Seed leaves a TODO for BIPOP CMA-ES, and 16 of 17 tests fail.
  - Wrong export path: Qwen3.6-Plus writes the classes but never re-exports them from
    `testing/__init__.py`.
  - Agent failure: Opus-4.6 spends 249 steps restructuring a monorepo, ends in an `ls | wc -l` loop,
    and writes zero decorators.

## 5. Mechanisms (the authors' explanations)
- **Partial progress then a stall.** Agents finish early targets and fail on later targets, on
  integration, or on correctness. The evidence is the gap between Completion Score and resolved rate,
  and the steep decline with target count.
- **Stronger models localise faster and switch sooner to targeted edits plus execution-based
  validation.** The evidence is that Opus-4.7 has the lowest Explore share (35%) with mid-range call
  volume, while GLM and Kimi spend more than half their calls exploring. This rests on correlation
  across 13 models; there is no intervention.
- **Extra steps help only if the model can convert them into edits.** The evidence is that most models
  plateau by about 200 steps while Opus-4.7 keeps improving.
- **The bottleneck moves with capability.**
  - Weak models fail at construction: the code does not build, or the feature is absent.
  - Strong models fail at execution precision: subtle logic errors, misreading the requirement, and
    wiring components together.
  - Evidence: the per-model taxonomy (Table 6).
- **Cascading build errors** are catastrophic for multi-target work. One broken shared module takes out
  every subtask (15.8% of all failures).
- **Creating new abstractions is harder than fixing defects.** The evidence is the 36% vs 64% pass rates
  by change type.
- **Scaffold format matters for mid-tier models.** Typed tool schemas help most of them; batched JSON
  helps GLM and Qwen. Top models are robust either way.
- **Under-specification looks like model failure.** The QC table shows that task-side defects depressed
  scores, most of all for the strongest model.

## 6. Recommendations (the authors')
- Evaluate long-horizon, multi-target development as its own setting. Use subtask-level partial-credit
  scoring alongside binary resolved rates, because it "offers cleaner separation across capability
  tiers".
- Build benchmarks with instruction–test alignment review (completeness, faithfulness, fairness,
  minimality). Use attribution-driven rollout QC to separate task defects from model limits before
  reporting results.
- Future work (App. A): metrics for code quality, maintainability and idiom beyond behavioural tests;
  more languages and ecosystems; more scaffolds.
- They position the benchmark as diagnostic. They make no explicit recommendations to practitioners.

## 7. Limits
**Stated by the authors (App. A):**
- Only two scaffolds were used, and results may differ on others.
- Tests check behaviour, not code quality, maintainability or idiom.
- Language and ecosystem coverage is limited.

**My own:**
- **Single trial per model, with no variance or CIs on the headline numbers.**
  - With n=115, one task is 0.87 pp. Domain cells hold 14–36 tasks, so one task is 2.8–7.1 pp.
  - Several "gaps" are within noise: GLM vs DeepSeek is tied at 18.3, and many lower-tier gaps are 1–3
    pp.
- **QC may be selection-biased.**
  - Tasks were repaired using rollouts from three model tiers. Table 4 suggests these were Opus-4.6,
    GLM-5.1 and Kimi-K2.5 on Terminus, which are evaluated models.
  - Finalisation required "distinguishable" tier scores, which tunes tasks to separate those models.
  - Claude-Opus-4.7 assisted static review, and Claude-Sonnet-4.6 classified failures. Both could
    favour Claude-style specs and readings.
- **Confounded comparisons.** Reasoning effort differs by model (xhigh for Opus-4.7, default for
  several others). Cross-model comparisons mix model and configuration.
- **Contamination is only argued, not tested.** These are popular OSS repos with public release notes.
  Many pre-2025 releases are probably in pre-training data. Git history up to the source release is
  available to the agent.
- **Unclear metric details.** Subtask weights "reflecting complexity" are not specified. The step
  budget is unclear: the setup says 2 h wall-clock, while Case 5 says "249-step budget".
- **Small internal inconsistencies.**
  - App. G.1 lists Java among the five languages, but the dataset is C++, not Java.
  - Table 4 gives Opus-4.6 "after" as 30.4%, but Table 2 has it at 31.3% on Terminus.
  - Kimi-K2.6 is cited as "MiniMax (2026a)".
- **Artificial setup.**
  - Autonomous single-shot runs, with no human in the loop and no clarifying questions.
  - The roadmap is carefully written and leak-checked, which is closer to an ideal spec than to a
    real ticket.
  - Tasks are libraries and frameworks with clean public APIs, not product apps with UI, database
    state and visual behaviour.
  - Each task is roughly a release, about 3,700 LOC. That is one to two orders of magnitude larger than
    a typical small bug-fix round.
- **Thin validation of the failure classifier.** 88% agreement on 50 samples, with sub-type accuracy
  lower. The sub-type percentages are soft.
- **Correlational mechanism claims.** Exploration share and success are correlated across 13 models.
  No ablation forces less exploration.

## 9. For wf (MY INFERENCE, not the paper's)
**Scale caveat first.** wf rounds are mostly small bug fixes and change requests. Two of the paper's
numbers suggest that is the regime agents handle well: subtask pass rates are highest for Bug Fix (64%),
and the same models score "80%+" on SWE-bench Verified. The paper's headline (39% resolved) is about
release-sized work and does **not** carry over to a typical wf round. What does carry over is the
**structure of failures** once a change spans several targets or files.

**What it supports in wf:**
- **One agent per commit, with `wf check` between commits.**
  - Resolved rate falls steadily with target count; at 7 or more targets the best model resolves 15%.
    Agents finish early targets and stall later. Slicing a round into commits with a deterministic gate
    after each is the right shape.
  - Cascading build errors are 15.8% of all failures: one broken shared import kills everything after
    it. A per-commit typecheck, lint and test run stops a cascade at the commit that caused it, before
    the next agent builds on top.
  - This argues for keeping `wf check` mandatory after **every** commit agent, not only at the end of
    the round.
- **Verification beats instruction, especially for strong models.**
  - With frontier models, 55–58% of failures are Implementation Errors: code that builds, mostly passes,
    and is subtly wrong. Examples are one operator in a formula (6 of 7 tests pass), Wiring Errors
    (parameters not forwarded) and Misunderstanding.
  - Lint and typecheck do not catch these. Behavioural checks do: the repro going red→green,
    validate's before/after measurements, and Shay reading the diff at T2.
  - The paper supports keeping the before/after validation and the critic. It suggests the critic
    should look specifically for wiring issues ("is the new thing actually reached from the entry
    point?") and for partial implementation ("is every plan item present?"). Together those are about
    36% of Opus-4.7's failures (Missing 29%, Interface/Wiring the rest).
- **T1 and plan quality matter a lot.** In the paper's own QC, fixing task-side spec and test defects
  raised Opus-4.6 from 19.1% to 30.4% resolved, the biggest gain of any model. 39% of their carefully
  built tasks had such defects. This is the strongest wf-relevant number in the paper: under-specified
  instructions look exactly like agent failure.
  - **Possible addition:** a cheap deterministic or LLM check over the plan and repro, using their
    per-target alignment axes:
    - completeness: every behaviour the repro or tests assert appears in the plan;
    - faithfulness: tests assert nothing the plan doesn't state;
    - fairness: no reliance on exact error strings or internal names unless the plan says so.
  - Their leakage list (internal names, pseudo-code, refactoring checklists) is a benchmark concern. In
    wf the plan is *meant* to say how, so that part does not apply.
- **Attributing failures, and "feedback given twice becomes infrastructure."** Their T-type vs M-type
  split (instruction gap, brittle test, environment, grading vs design, implementation bug, debugging)
  is a usable label set for wf's critic or post-round notes. When a commit agent fails, record whether
  the plan, the test or the env was at fault, or the agent. Recurring T-types are what to turn into
  checks.
- **Research before plan and implementation.** Strong models do better because they localise quickly
  (Opus-4.7 spends 35% of calls exploring; weaker models more than 50%). wf's research phase already
  hands localisation to later agents. Commit agents should receive file and line pointers from research
  and the plan, not rediscover them. This is correlational evidence only.
- **Harness complexity worry.** Top models are scaffold-robust (Opus-4.6 moves 0.9 pp across two quite
  different scaffolds; Opus-4.7 moves 0.8 pp). Fine-tuning the harness's prompt and tool format buys
  little for frontier models. Spend harness complexity on deterministic checks, not on agent-loop
  tweaks.
- **Budgets and loop guards.** Most models plateau by about 200 steps. The Opus-4.6 case burned 249
  steps on restructuring and an `ls | wc -l` loop with zero output. A per-commit-agent step or time cap
  with a "no file changed in N steps" tripwire is cheap and stops a runaway round. This is a
  suggestion; the paper doesn't test such a guard.

**What it suggests watching:**
- **Creating new components is the hard class** (36% subtask pass rate vs 64% for bug fixes). In change
  requests that introduce a new abstraction, module or component, the plan at T1 deserves more
  attention, and perhaps a smaller commit slice. Plain bug-fix rounds can stay light.
- **Missing re-exports and wrong paths** (Interface Mismatch 6.5%) are concrete in JewelryX too: Python
  `__init__` exports, FastAPI router registration, SvelteKit route and file conventions. A standards
  rule or check that "new symbol is reachable from the public entry or router" would catch some of
  these deterministically.

**Where it does NOT apply:**
- **Task size.** wf rounds are tens to hundreds of LOC, not about 3,700, so absolute success rates do
  not transfer.
- **No humans.** Runs are autonomous single-shot with no T1 or T2, no clarifying questions, and no
  iteration across rounds. They say nothing about how human gates change outcomes.
- **Code type.** Tasks are libraries and frameworks in Python, TS, Go, Rust and C++ with clean public
  APIs and upstream test suites. There is no product app, no SvelteKit UI, no MongoDB state, and no
  visual verification, so before/after screenshots have no analogue here.
- **No compounding.** Evaluation is behavioural tests only, so code quality, maintainability and the
  "codebase teaches the next change" effect are unmeasured. Nothing here speaks to compounding over
  agent-written code across rounds. wf's `wf standards` agents cover a dimension this paper explicitly
  doesn't.
- **Noise.** It is a single trial per model, so the finer model-vs-model and domain differences should
  not drive any wf decision.
