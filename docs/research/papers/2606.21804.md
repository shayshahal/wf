## 2. Question
When a *future agent* has to build on code, does it matter whether that code was written by an agent or by a human? The authors measure maintainability by downstream task success, not by static metrics: same downstream task, same downstream agent, same tests, and only the authorship of the intermediate code varies. They also ask *what* in agent code causes the downstream failures, and whether classic maintainability metrics (cyclomatic complexity, cognitive complexity, Halstead volume, LLOC) capture it.

## 3. Method
**CodeThread framework (§3, Fig. 2).** It starts from an issue-resolution benchmark instance: an issue, a base commit, the human gold patch, and tests (Fail-to-Pass, F2P; Pass-to-Pass, P2P).
- **PR0 (skeleton):** the bodies of the target functions are removed and their signatures kept.
- **Implementation Task (PR0→PR1):** an LLM writes an issue/docstring asking for the missing functionality to be restored. The Fig. A1 prompt asks for a summary, arguments, returns, exceptions, implementation notes and edge cases, without revealing the body. The agent implements it, producing agent PR1. The human PR1 is the original code. **Filter:** agent PR1 must pass *all* P2P tests (functionality restored) and still fail *all* F2P tests (the downstream issue is not already solved). So "the target methods are functionally equivalent across the two PR1 versions" as far as the existing tests can see.
- **Follow-On Issue (PR1→PR2):** the original benchmark issue, unchanged, applied on top of PR1. It is resolved if all P2P and all F2P tests pass.
- **Conditions:** HH (the original human PRs), **HA** (human PR1 + agent PR2), **AA** (agent PR1 + agent PR2). The key comparison is **AA vs HA**, which holds the PR2 author fixed. AH (a human building on agent code) is **not** studied.
- **Metric:** PR2 resolve rate (%). Maintainability is "task-based": how often the next agent succeeds.

**Benchmarks (Table 1).** After keeping only instances that need function-level edits, 1,377 of 1,687 instances remain, across 78 repos and 10 languages:
- SWE-Bench Verified: 441/500, 12 repos, Python, bug fix. Average PR1 1.12 files / 1.60 functions; PR2 1.18 / 1.71.
- SWE-Bench Multilingual: 171/300, 34 repos, 7 languages, bug fix. PR1 1.29 / 1.90; PR2 1.84 / 3.28.
- SWE-Bench Pro: 641/731, 11 repos, 4 languages, bug fix, feature and refactor. PR1 2.43 / 5.51; PR2 5.22 / 10.70.
- FeatBench: 124/156, 22 repos, Python, feature implementation. PR1 1.52 / 2.54; PR2 2.35 / 4.03.
- Languages in the examples include Python, C, Go and TypeScript; one TypeScript example is a frontend UI change.

**Agents (§4.1, App. C).**
- Models: Claude 4.5 Sonnet, GPT-5 (both via API), GLM 4.7 FP8 and MiniMax M2.5 (both self-hosted on vLLM).
- All four run in the **SWE-agent** scaffold with one shared configuration: a 250-step limit, a $3/instance cost cap, and high reasoning effort.
- **One run per (model, condition, instance).** There are no repeated seeds.
- To save cost, the Claude and GPT-5 runs on Pro, Multilingual and FeatBench are limited to instances whose PR1 gate passed for both MiniMax and GLM.
- These are not the vendors' own products (Claude Code, Codex).

**Comparisons.**
- Main table (Table 2): the subset of instances shared by all four models within each benchmark.
- Table A1: every instance that passed the filter, per model.
- Table 3: results by task type. N: BF 210, FI 104, RF 70, FI+RF 22.
- My inference from the step sizes in Table 2: the shared sets are about 99 (Verified), 32 (Multilingual), ~259 (Pro) and 16 (FeatBench) instances. The paper states only FeatBench's 16. A 1.0-pt change on Verified is one instance; a 6.2-pt change on FeatBench is one instance.
- **No significance tests or CIs are reported for the HA–AA resolve-rate gaps.**

**Root-cause analysis (§5).**
- Unit of analysis: the *discordant* instances, where HA and AA give different outcomes. There are 454 across all models and benchmarks. 405 remain after removing instances with incomplete features (64.7% HA wins, 35.3% AA wins).
- Model: logistic regression with Y=1 if HA resolves and AA fails, plus benchmark and model fixed effects. Twelve features:
  - (a) Static metrics as AA−HA deltas at PR1 and PR2: CC, CogC, HV and LLOC. Tools: radon, complexipy, rust-code-analysis-cli, lizard, gocognit, and a custom go-halstead.
  - (b) Patch localization at PR2: Jaccard overlap of the files and of the functions edited by HA vs AA.
  - (c) **IEC** (input/error contract) drift on agent PR1. A binary flag set if an LLM judge (DeepSeek-V4 Pro) labels the primary drift category Input Gating, Silent Fallback or Error Handling. It uses a 10-category taxonomy (Table A5) and was run on 2,517 records.
  - (d) Difficulty control: the leave-one-out mean resolve rate of the other three models on the same instance.
- ORs above 1 tilt toward HA winning. The paper does not say whether features were standardized, so the per-unit size of the LLOC OR is unclear.

**Drift taxonomy (Table A5).** The judge picks one primary category per instance.
- A, compatible: EQUIVALENT, STYLE, ALGORITHM.
- B, behavioral divergence: INPUT GATING, SILENT FALLBACK, ERROR HANDLING, RETURN SHAPE, EXTERNAL EFFECTS.
- C, scope: EXTRA EDITS.
- D, failure: INCOMPLETE.

**Judge validation.**
- Human verification audit (App. D.5): 50 instances, stratified with rare labels oversampled, 29 repos. The auditor saw the judge's label. 48/50 (96%) IEC vs non-IEC calls were confirmed; 2 moved from IEC to non-IEC.
- Second judge (App. D.6): Kimi K2.6 relabelled the 405 discordant instances.

**Causal attribution (§5.3, App. D.4).** On the HA-win cohort with a divergent agent PR1 (n=262; 30 EQUIVALENT/STYLE cases excluded), an LLM judge (DeepSeek-V4 Pro) decides whether the drift survived into PR2 and whether the failing test traces back to it.

**Main gaps (Table 2, shared instances; PR2 resolve rates, HA → AA, Δ in points):**

| Benchmark | Claude 4.5 Sonnet | GPT-5 | GLM 4.7 | MiniMax M2.5 |
|---|---|---|---|---|
| SWE-Bench Verified | 71.7 → 66.7 (−5.1) | 62.6 → 61.6 (−1.0) | 65.7 → 62.6 (−3.0) | 74.7 → 68.7 (−6.1) |
| SWE-Bench Multilingual | 53.1 → 50.0 (−3.1) | 46.9 → 50.0 (+3.1) | 62.5 → 59.4 (−3.1) | 65.6 → 62.5 (−3.1) |
| SWE-Bench Pro | 46.3 → 38.6 (−7.7) | 39.0 → 39.8 (+0.8) | 45.2 → 32.0 (**−13.1**) | 43.6 → 36.7 (−6.9) |
| FeatBench (n=16) | 50.0 → 56.2 (+6.2) | 56.2 → 43.8 (−12.5) | 62.5 → 56.2 (−6.2) | 56.2 → 56.2 (0.0) |

- AA is worse in 12 of 16 cells, equal in 1, and better in 3. The headline "up to 13.1%" is GLM 4.7 on SWE-Bench Pro.
- The authors discount the positive cells. GPT-5's +3.1 and +0.8 come with a lower HA baseline ("a weaker ceiling"). Claude's +6.2 on FeatBench is "our smallest overlap set of 16 instances".
- GLM is the most consistent: AA is worse on every benchmark. GPT-5 shows the smallest gaps on the SWE-Bench variants but −12.5 on FeatBench, from which they suggest "maintainability costs may be more visible on feature implementation tasks".

**Full per-model sets (Table A1; N per cell in brackets), same direction:**
- Verified: Claude −1.4 (215), GPT −3.2 (186), GLM −2.9 (207), MiniMax −4.72 (233).
- Multilingual: Claude 0.0 (38), GPT +2.8 (36), GLM −13.8 (58), MiniMax −2.5 (86).
- Pro: Claude −8.0 (313; 141 vs 116 resolved), GPT +1.0 (280), GLM −11.1 (397; 179 vs 135), MiniMax −4.3 (395).
- FeatBench: Claude +5.8 (17), GPT −11.7 (17), GLM −9.5 (42), MiniMax −7.5 (40).
- That is 12 of 16 negative, 1 zero, 3 positive.
- Small inconsistency: these instance counts sum to 2,560, while the judge "run on 2,517 records, one for every instance". Not explained.

**By task type (Table 3, average Δ across models):**
- Refactoring −8.21 (N=70). GLM −15.71 and MiniMax −12.86 here.
- FI+RF −6.82 (N=22).
- Feature implementation −6.25 (N=104). GLM −15.38.
- **Bug fix −4.05 (N=210, the smallest).** GPT is +0.48 here.
- Consistent with prior work that refactoring and multi-file edits are harder than localized fixes.

**Discordance (§5).** 454 discordant instances: 64.3% are HA wins and 35.7% are AA wins (about 292 vs 162, my arithmetic). So a large share of the disagreement runs the "wrong" way too, i.e. it is noise from single-run agents. The net asymmetry is the effect.

**Logistic regression (Table 4, n=405, OR with 95% CI and p):**
- PR1 static deltas, all null:
  - ΔCC 0.92 (0.53–1.61), p=.779
  - ΔCogC 1.00 (0.67–1.48), p=.981
  - ΔHV 1.03 (0.69–1.53), p=.885
  - ΔLLOC 0.92 (0.53–1.61), p=.780
- PR2 static deltas:
  - ΔCC 0.71 (0.38–1.31), p=.271
  - ΔCogC 0.97, p=.866
  - ΔHV 0.93, p=.615
  - **ΔLLOC_PR2 1.88 (1.02–3.46), p=.042.** AA's PR2 adds more lines than HA's ("over-editing") when HA wins.
- Localization:
  - File Jaccard 0.77 (0.58–1.01), p=.061
  - Function Jaccard 1.22 (0.93–1.60), p=.144
- **IEC 1.83 (1.15–2.92), p=.011.** Agent PR1 changed input validation or error handling.
- **Instance resolve rate (LOO difficulty) 1.42 (1.12–1.78), p=.003.** HA wins happen on easier instances.
- Model fit: **McFadden R² = 0.069**, LR χ²(18)=36.1, p=.007. The authors call this "modest but reliable": informative but not predictive.
- Fig. 3 shows the same picture: static metric distributions are near-identical for HA wins vs AA wins, and only IEC, ΔLLOC_PR2 and difficulty separate them.

**Judge robustness (App. D.6, Table A6).** With Kimi K2.6 as the judge: IEC OR 1.70 (p=.039), ΔLLOC_PR2 1.83 (p=.042), difficulty 1.42 (p=.003). The same three features stay significant with the same signs.

**Drift persistence and causation (§5.3, Table A4, n=262 HA-win instances with a divergent agent PR1):**
- **Drift survived PR2 unchanged: 225 (85.9%).** Partially corrected: 19 (7.3%). Rewritten or corrected: 18 (6.9%).
- Failing test traced to the surviving drift: **54 (20.6%)**. Unrelated failure: 195 (74.4%). Unclear: 12 (4.6%). N/A: 1.
- So per-instance causation is confirmed for about a fifth of the HA-win failures. Three quarters are unexplained.

**Qualitative examples (App. D.7, five cases across C, Go, Python and TypeScript):**
- A silent fallback (C): the agent prints the error and continues instead of returning 0.
- Added input gating (Python).
- Removed input gating (Python): the agent accepts two list arguments that the human code rejected.
- Changed error handling (Go): the heartbeat is not stored on err==nil.
- Added gating in a TypeScript frontend: the agent added a `disabled` property, so the dialog never opens and all 9 follow-up tests fail. The PR2 agent also *copied the pattern onto a newly added option*.

## 5. Mechanisms
- **Input/error-contract drift.** Agents silently change observable edge behavior: they add guard checks that raise or return early (e.g., an extra `ValueError`), coerce inputs (`getattr(x, …, None)`, `dict.get(k, default)`, `x or default`), or raise, catch or wrap exceptions differently. Existing tests do not catch it: by construction agent PR1 passed every P2P test. The next agent builds on it, and the downstream tests fail.
  - Evidence: the IEC OR is 1.83, robust across two judges with a 96% audit confirmation rate. Drift persists into PR2 in 85.9% of cases, and per-instance causation is confirmed for 20.6%.
- **Over-editing downstream.** When the AA PR2 grows more than HA's PR2 (ΔLLOC_PR2, OR 1.88), HA tends to win. The authors treat this as a summary statistic, not a verified mechanism. One reading: unfamiliar or odd code leads the next agent to write more code around it.
- **Task difficulty.** HA wins are concentrated on easier instances (OR 1.42). Harder instances fail in both conditions, so they cannot be discordant.
- **What does *not* explain it:** structural complexity and verbosity of the agent's own code (CC, CogC, HV, LLOC at PR1), and localization (which files or functions PR2 touched).
- **Compounding:** because drift persists (about 86%), the authors argue it "could compound across PRs" on longer chains. This is untested; they only ran 2-step chains.
- The authors do *not* analyze why agents drift. That the PR1 prompt spelled out exceptions and edge cases yet agents still diverged is my observation from App. A, not their claim.

## 6. Recommendations (the authors')
- Evaluate coding agents "not only by immediate task resolution but also by maintainability". Evaluation "must shift from isolated task completion toward long-term maintainability".
- Static maintainability metrics alone are insufficient. Look at behavioral, contract-level differences.
- Ethics section: the findings underscore "the need for benchmarks, review practices, and safeguards that evaluate coding agents beyond immediate task completion". They are "not … evidence against the use of coding agents broadly".
- Future work:
  - longer PR chains with function-level overlap, to test compounding;
  - the AH condition (humans building on agent code), on a smaller curated subset;
  - isolating the 74.4% of failures not explained by drift.

## 7. Limits
**Stated by the authors:**
- Only 2-step chains, so no long-horizon compounding is measured.
- The PR1 filter (agent must not already solve F2P) may introduce selection bias. It retains "a large majority", and they say incidental solves are common.
- No AH condition, so nothing is learned about humans maintaining agent code.
- One run per instance, chosen for cost.
- The FeatBench overlap is small (16).
- The positive GPT-5 cells may reflect a low ceiling.

**My own:**
- **No statistical test on the headline gaps.** The deltas in Table 2 are single-run point estimates on small shared sets, where one instance is 1–6 points. The consistency across 12 of 16 cells, plus the 64/36 discordance split, is the real evidence. Per cell it is weak.
- **Home-advantage confound.** The human PR1 is the code the original F2P tests were written against. The follow-on tests encode the human's exact contracts (which exception, which default, which input is rejected). "Agent code is less maintainable" is therefore partly "agent code deviates from the hidden contract that downstream tests assume". That is still a real cost in a real repo, where later code and tests rely on existing contracts. But it is not a neutral measure of maintainability. The paper does not discuss this. The IEC finding is exactly this kind of deviation.
- **Artificial setup.** The agent re-implements *removed* function bodies from an LLM-written docstring inside an otherwise human repo. Real agent code is written from a ticket, shapes its own surroundings, and passes human review. Here PR1 is accepted on tests alone, with no review, critic or human gate.
- **Model generations and scaffold.** Sonnet 4.5, GPT-5, GLM 4.7 and MiniMax M2.5, all in SWE-agent with a $3 cap. These are not today's harnesses (Claude Code, Codex) and not newer models.
- **Weak regression.** McFadden R² is 0.069, and ΔLLOC_PR2 is marginal (CI lower bound 1.02). The IEC label comes from an LLM judge, checked by a non-blind audit where the auditor saw the label.
- **Causation is thin.** It is confirmed (by an LLM judge) for only 20.6% of HA wins.
- **Benchmark repos are popular OSS libraries**, mostly with backend and library code. They are multi-language (not Python-only), but there is only one frontend example.
- **Unexplained discrepancy:** 2,560 vs 2,517 records.

## 8. Quotes
1. "we find that agents are less effective at resolving tasks when building on agent code compared to human code, with task resolve rate drops of up to 13.1%." (Abstract)
2. "Regression analysis reveals that many traditional software engineering maintainability metrics do not explain this difference." (Abstract)
3. "From our observations, differences in exception types or swapped defaults can silently creep into the codebase." (§5.1)
4. "When agent PR1 alters input-validation or error-handling behavior, the odds of HA winning are 1.83× that of AA, and when AA's PR2 adds more lines than HA's, HA is 1.88× more likely to win over AA." (§5.3)
5. "PR2 rewrites the divergent function on only 6.9% of instances, while the drift is unchanged in 85.9% of instances." (§5.3)
6. "Bug-fix tasks show the smallest average drop, with an average 4.05%." (§4.2)
7. "building on agent code often introduces maintainability costs, which appear even on two-step chains and are likely to compound over many edits of a software project." (§6 Conclusion)

## 9. For wf (MY INFERENCE, not the paper's)
**What it supports**
- **"The codebase teaches the next change"** gets direct experimental backing. The next agent does worse on agent-written code: about −4 pts on bug fixes, −6 on features, −8 on refactors (average over 4 models). The odd behavior is *inherited, not repaired*: drift survives the next PR in 86% of cases. The TypeScript example shows the PR2 agent copying the agent's `disabled` gating onto a new option. In wf, every round builds on earlier agent rounds, so whatever passes T2 becomes the template. This raises the value of T2 and of anything that keeps contract drift out of `main`.
- **"Verification beats instruction."** In App. A the PR1 prompt *spelled out* the returns, raised exceptions and edge cases, yet agents still drifted on exactly those points. More instruction in the plan or prompt is unlikely to fix this; a check is.
- **Bug-fix-heavy workload.** The smallest gap is on bug fixes (−4.05) and the largest on refactors and features. wf's mix of mostly small fixes is the least exposed case. Change requests that look like features or refactors deserve more scrutiny at T1 and T2.

**What it suggests adding (concrete, cheap)**
- **A "contract drift" rule in `wf standards` / the critic.** One rule-agent compares the pre- and post-change behavior of every function the round touched, using the paper's Group B categories:
  - input gating added or removed (new early `raise`/`return`/`assert`, or a new `disabled`/guard in Svelte);
  - silent fallback (`dict.get(k, default)`, `x or default`, `getattr(..., None)`, `?? default`, `int(x)` coercion, Pydantic defaults in FastAPI models);
  - changed exception type or handling (catch vs propagate, a different `HTTPException` status);
  - a changed return shape (`None` vs `[]`, different dict keys);
  - new external effects.

  Output: a short list, "function X now rejects/accepts/defaults Y". It goes into the T2 packet next to the diff, so Shay's scarce attention lands on the 1–3 behavioral changes rather than on style. The paper shows an LLM judge with this taxonomy is reliable enough for the IEC vs non-IEC call (96% confirmed on audit, robust across two judges). This is a rule-agent, which fits the existing `wf standards` pattern, not new harness machinery.
- **Make it deterministic where possible ("feedback twice → infrastructure").** Silent fallback overlaps with lint-kit's error-handling set, which already requires that a `catch` dropping an error say why. If the contract-drift agent flags the same pattern twice in JewelryX, promote it to a lint rule. Two cases: a new `except: pass` or a broad `except Exception` returning a default in FastAPI handlers, and `.get(..., default)` on request payloads.
- **Pin intentional contract changes with tests.** All drift in the paper passed existing tests (the P2P filter) and was only caught by *later* tests. In wf, `wf check` proves the repro goes red→green and that existing tests stay green, which is exactly the P2P situation. Proposed rule: if the contract-drift list is non-empty and the change is intended, the commit agent adds a test asserting the new edge behavior. If it is not intended, the change is reverted before T2.
- **Bound the downstream diff size.** ΔLLOC_PR2 (OR 1.88) and the EXTRA EDITS category say over-editing goes with failure. The plan (T1) could state an expected file/function scope. `wf check` or the critic flags commits that touch functions outside the plan, or exceed it by a large margin. Show the scope in the T2 summary.

**What it argues against / not to add**
- **Don't add static-complexity gates** (cyclomatic, cognitive, Halstead, LLOC thresholds) to `wf check` on the theory that they catch agent debt. At PR1 they had ORs of about 1.0 with p≥.78. This is harness growth with no predictive payoff, which feeds the "harness more complex than the app" worry.
- Don't treat "tests green" as evidence of maintainability. By construction, the agent code in this paper was test-green.

**Where it does NOT apply / how far to trust it for wf**
- The paper's agent PR1 had **no review, no plan gate, no critic and no human**. It was accepted on tests alone. wf has T1, T2, a critic and rule-agents, so the paper's gap is closer to an upper bound for wf. That holds only if those gates actually look at edge-case contracts. A diff skim can miss a silent `?? default`, so the effect may survive human review.
- The **AH case is untested**: whether Shay or a teammate finds agent code harder to maintain is not answered here.
- The setup re-implements deleted function bodies against a docstring in human-written OSS libraries, with SWE-agent and 2025-era models (Sonnet 4.5, GPT-5). It is not SvelteKit/FastAPI/MongoDB app code, not ticket-driven, and not today's harness. The effect sizes are single-run, small-n and untested for significance. Treat the *direction* and the *mechanism* (contract drift persists and gets copied) as the takeaway, not the magnitudes.
- Part of the measured cost is deviation from contracts that the original tests assume (the home-advantage confound in §7). For wf that is still the relevant cost: JewelryX code and tests rely on existing contracts. It also means the fix is contract checking, not "make code simpler".
- Chains are only 2 steps. wf's long chains of agent-on-agent rounds are exactly the untested compounding regime. The persistence data (86%) suggests it gets worse, not better, over many rounds.
