## 1. Citation
- **Title:** SWE-CI: Evaluating Agent Capabilities in Maintaining Codebases via Continuous Integration
- **Authors:** Jialong Chen (Sun Yat-sen University; Skylenage), Xander Xu (Alibaba Group), Hu Wei (Alibaba), Chuan Chen (Sun Yat-sen), Bing Zhao (Alibaba, corresponding). Chen and Xu contributed equally.
- **Date / version:** v1 submitted 4 Mar 2026; read **v4, 1 Apr 2026** (arXiv cs.SE). No venue stated (preprint).
- **Link:** https://arxiv.org/abs/2603.03823 (HTML: https://arxiv.org/html/2603.03823v4). Data: huggingface.co/datasets/skylenage/SWE-CI; code: github.com/SKYLENAGE-AI/SWE-CI.

## 2. Question
Snapshot benchmarks (HumanEval, SWE-bench, Terminal-bench) give one requirement and score one solution, so a brittle hard-coded fix and a clean extensible one score the same. The authors ask whether agents can *maintain* a codebase: when they change it repeatedly over many iterations, each built on their own earlier changes, does functional correctness hold up and keep improving, or do regressions and debt build up? They operationalise maintainability as "functional correctness on future modifications".

## 3. Method
**Formalisation (§2.1).** `require(c_i, c*)` produces a requirement from the test gap between the current codebase c_i and the oracle c*; `code(c_i, r_i)` produces c_{i+1}. Requirements are regenerated from the *current* code every iteration, so earlier decisions propagate.

**Normalized change (§2.2, Eq. 2).** n(c) = number of tests (from the oracle's test suite) passing on c.
- If n(c) ≥ n(c0): a(c) = (n(c) − n(c0)) / (n(c*) − n(c0)), so 1 = gap fully closed.
- Else: a(c) = (n(c) − n(c0)) / n(c0), so −1 = every initially passing test broken. Range [−1, 1].

**EvoScore (§2.3, Eq. 3).** Weighted mean over iterations i=1..N: e = Σ γ^i a(c_i) / Σ γ^i. They argue for γ ≥ 1, which weights later iterations more, so an agent that builds a clean base early gets rewarded. **Headline numbers use γ = 1, which makes EvoScore the plain mean of normalized change** (Fig. 4 y-axis "EvoScore(γ=1)"). The γ sweep tests only 0.8–1.2 (Fig. 5).

**Dataset (§3.1).**
1. All GitHub Python repos with ≥3 years of maintenance, >500 stars, pyproject/lockfiles plus a unit test suite, permissive licence → 4,923 repos.
2. Main branch only, made linear. Find maximal commit runs with unchanged dependencies; the endpoints become base/oracle pairs; keep pairs with ≥1,000 modified LOC → 8,311 pairs.
3. Auto-generate a Dockerfile from the oracle's dependencies and run the oracle tests. A "self-repair" step injects missing dependencies. Pairs that fail for other reasons are dropped → 1,458.
4. Run the oracle tests on the base and drop pairs where they fail to launch. Drop pairs whose passing-test counts differ by <5 → 137. Rank by time span and number of commits and keep the top 100.

Final set: **100 tasks from 68 repos**, on average **233 days and 71 commits** between base and oracle, each with ≥500 changed source lines (tests excluded). **Python only.** Each task ships a Docker image.

**Dual-agent protocol (§3.2, prompts in App. C).**
- **Architect** reads the failing tests (`/app/non-passed/summary.jsonl` plus the test files) and the source, then follows summarize → trace → attribute → filter → document. It writes `requirement.xml` with **1–5 requirements**, each with location, description, a behavioural *contract*, and *acceptance* criteria. It must stay high-level (no implementation) and must not tell the programmer to touch the tests. Priority rules: the change that unblocks the most failing tests first; error/collection/import before failed before missing; low-level shared modules before specific cases; base capabilities before upper-level behaviour. **The Architect is forbidden to run tests.**
- **Programmer** reads the requirements and the code, then plans and implements. "Principle of necessary changes", no scope expansion. It must not edit the tests or `requirement.xml`. **It is also forbidden to run tests** ("Verification work is completed by an external system").
- After each iteration an external harness runs pytest and compares against the frozen oracle report (Fig. 3).

**Setting (§4.1).** pytest + pytest-json-report, 3,600 s timeout per test run, **iFlow CLI** as the harness, **max 20 iterations**. Architect and Programmer use the same model. More than **10 billion tokens** in total.

**Models (20 from 8 providers):** Claude Opus 4.5 and 4.6; GPT-5.2 and GPT-5.4 (2026-03-05); GLM-4.6, 4.7, 5; Qwen3-coder-plus, Qwen3-Max (2025-09-23 and 2026-01-23), Qwen3.5-plus; DeepSeek-V3.1 and V3.2; Kimi-K2-Instruct-0905, K2-Thinking, K2.5; MiniMax-M2.1 and M2.5; Doubao-seed-1.8 (251228) and 2.0-pro (260215).

**Other metrics.**
- Zero-regression rate: share of the 100 samples with no regression at any point.
- Regression rate and magnitude per iteration. Neither is formally defined. "Magnitude" appears to be the share of the test suite a regression affects. The authors correlate each with the iteration index (Pearson).
- Pylint score and Radon-style Maintainability Index (MI), compared LLM vs human oracle as win/loss on **successfully solved problems only**. The scope (whole repo or touched files) is not stated.
- Changed lines, LLM vs human.
- Solved rate (all oracle tests pass by the end; the γ→∞ limit).
- Average turns used.
- Cumulative max relative change by turn bin.

**Baselines / sample sizes.** No non-LLM baseline. The human oracle serves only as the comparison for style and diff size. As far as the paper says, there is **one run per model per task**: no seeds, variance, CIs or significance tests are reported. There is **no ablation of the dual-agent design**, of the 5-requirement cap, or of the no-test-execution rule.

## 4. Results
All values are read off the figures. EvoScores are approximate (read from the plot at ±0.01); percentages are printed labels.

**EvoScore, γ=1 (Fig. 4, §4.2, Obs. 1).** Within each provider, newer models always score higher, and gains are larger for models released in 2026.
- Claude Opus 4.6 ≈ **0.92**; GLM-5 ≈ 0.71; Claude Opus 4.5 ≈ 0.70.
- Qwen3.5-plus ≈ 0.60; MiniMax-M2.5 ≈ 0.59; GPT-5.4 ≈ 0.58.
- DeepSeek-V3.2 ≈ 0.49; GLM-4.7 ≈ 0.48; Kimi-K2.5 ≈ 0.47; GPT-5.2 ≈ 0.44.
- Kimi-K2-thinking ≈ 0.39; Kimi-K2-Instruct-0905 ≈ 0.38; GLM-4.6 ≈ 0.38; MiniMax-M2.1 ≈ 0.37.
- Qwen3-Max-2026-01-23 ≈ 0.32; Qwen3-Max-2025-09-23 ≈ 0.31; Doubao-seed-2.0-pro ≈ 0.29; Doubao-seed-1.8 ≈ 0.27; Qwen3-coder-plus ≈ 0.24.
- DeepSeek-V3.1 ≈ **0.07**.

**γ sensitivity (Fig. 5, Obs. 2).** Rankings shift at γ = 0.8 → 1.2:
- Short-term-leaning providers lose rank: MiniMax-M2.1 #11→#14, GPT-5.2 #8→#11, GPT-5.4 #4→#6, DeepSeek-V3.2 #7→#9.
- Long-term-leaning providers gain: Kimi-K2-Instruct #14→#10, Kimi-K2.5 #10→#7, Qwen3.5-plus #6→#4, GLM-5 #3→#2.
- Claude Opus 4.6 is #1 and Qwen3-coder-plus #19 / DeepSeek-V3.1 #20 at every γ. Opus 4.5 drops #2→#3.
- The authors read this as provider-level training differences. That is a conjecture.

**Zero-regression rate (Fig. 6, §4.3, Obs. 3)** — the key negative result. Most models are below 25%, and only the two Opus models exceed 50%.
- Claude Opus 4.6 **76%**, Opus 4.5 **51%**.
- Kimi-K2.5 37%, GLM-5 36%.
- GPT-5.4 23%, GPT-5.2 23%; DeepSeek-V3.2, Qwen3.5-plus and MiniMax-M2.5 20% each.
- Kimi-K2-Thinking 15%, MiniMax-M2.1 15%; GLM-4.7 14%, GLM-4.6 14%; Kimi-K2-Instruct 12%; DeepSeek-V3.1 11%; Qwen3-coder-plus 10%.
- Doubao-1.8 9%, Qwen3-Max-2026 9%, Doubao-2.0 8%, Qwen3-Max-2025 **7%**.

So **even the best model broke previously passing tests at some point in 24% of tasks**, and the median model did so in ~85%.

**Regression trend over iterations (Fig. 7, Obs. 4).**
- Regression *rate* correlates positively with iteration count for **12/20** models. Examples: Opus 4.5 r≈0.99, GLM-5 ≈0.93, MiniMax-M2.5 ≈0.89, Opus 4.6 ≈0.87, GPT-5.2 ≈0.75.
- 4 models show no trend. 4 are negative: DeepSeek-V3.1 ≈−0.97, GLM-4.6 ≈−0.92, GPT-5.4 ≈−0.80, Kimi-K2-Instruct ≈−0.75.
- Regression *magnitude* correlates negatively for **11/20** models, positively for 5 (Opus 4.5 ≈0.85, Qwen3.5-plus ≈0.75, MiniMax-M2.5 ≈0.68, Kimi-K2-Thinking ≈0.58, DeepSeek-V3.2 ≈0.38), with 4 showing no trend (Opus 4.6 ≈0.15).
- The figure's "no trend" band appears to be |r| < 0.3.
- In short, regressions become more frequent but smaller as iterations go on.

**Style vs maintainability (Fig. 8, §4.4, Obs. 5)** — the most striking result.
- On Pylint, **15/20** LLMs beat the human oracle more often than not. GPT-5.4 wins 72%, MiniMax-M2.1/M2.5 and GPT-5.2 68%, GLM-5 64%, Opus 4.5 62%, Opus 4.6 60%. The worst is Qwen3-coder-plus at 31%.
- On MI, **20/20** LLMs lose to the human oracle more often than they win.
  - Best: Opus 4.5, worse than human 58% of the time.
  - Opus 4.6 is worse 66% of the time, GLM-5 65%.
  - Worst: **GPT-5.4, worse 84%** — even though it is the *best* on Pylint.
- Code is "superficially clean but intrinsically complex".

**Diff size (Fig. 9, Obs. 6).**
- For every model, nearly all points fall below the diagonal: the LLM changes fewer lines than the human oracle for the same task. Human diffs run ~10³–10⁵ lines; LLM diffs mostly 10²–10³.
- There are visible outliers of ~10⁶ LLM-changed lines: one each for Opus 4.5, Opus 4.6, GLM-5 and GPT-5.2, and several for Doubao-1.8. These are probably generated or vendored files; the paper does not discuss them.
- The authors' reading: the extra human lines are "purposeful investments" (abstraction, encapsulation, modularisation), while LLMs make minimal changes.

**Solved rate (Fig. 10, App. B.1, Obs. 7).**
- Opus 4.6 **91%**, Opus 4.5 67%, GLM-5 64%, Qwen3.5-plus 62%, MiniMax-M2.5 52%.
- DeepSeek-V3.2 43%, Doubao-1.8 41%, GLM-4.7 40%, GPT-5.4 40%.
- Kimi-K2-Instruct 35%, Kimi-K2-Thinking 35%, Doubao-2.0 32%, GLM-4.6 30%, Kimi-K2.5 30%.
- Qwen3-Max-2026 29%, GPT-5.2 28%, MiniMax-M2.1 23%, Qwen3-Max-2025 23%, Qwen3-coder-plus 19%, DeepSeek-V3.1 **8%**.
- Most models are below 50%. The ranking roughly matches EvoScore.
- Oddity: Kimi-K2.5 has the 3rd-best zero-regression rate (37%) but solves only 30%, so not regressing partly reflects doing less.

**Average turns (Fig. 11, Obs. 8), max 20.**
- Opus 4.6 **5.3**, Opus 4.5 9.8, GLM-5 12.2, Qwen3.5-plus 13.4, MiniMax-M2.5 14.1, GPT-5.4 14.5, DeepSeek-V3.2 15.9, GPT-5.2 16.4.
- The rest sit at 16.5–18.5. DeepSeek-V3.1 uses **19.6**.
- Weak models use up the budget without finishing: "the bottleneck lies in model capability rather than the number of attempts".

**Gains by turn (Fig. 12, Obs. 9).** Cumulative max relative change rises most steeply in turns 1–4 and flattens after about 8.
- Opus 4.6 is ~82% by turns 1–4, ~96% by 5–8, and ~98% at the end.
- Opus 4.5 goes ~61% → ~82% → ~89%.
- GLM-5 goes ~52% → ~78% → ~91%.
- DeepSeek-V3.1 goes ~0% → ~20% → ~38%.
- Weaker models keep climbing slowly through turn 20.

## 5. Mechanisms (as the authors claim them)
- **Snapshot tests hide design quality.** Debt shows up only when later changes must build on earlier ones (§1). The evidence is the design itself: EvoScore and regression results differ across models in ways a single pass/fail would not show. They do **not** show that a low EvoScore is *caused* by poor earlier design rather than by plain inability to solve later tests. There is no counterfactual, e.g. resuming from the human oracle's intermediate commits.
- **Rising regression rate and falling magnitude** come from task structure: easy requirements get solved early, then models fall back on "trial-and-error on harder problems", making more frequent but more localised edits (§4.3). This is labelled a conjecture, with no supporting analysis.
- **Pylint wins but MI losses** show that LLMs learn "explicit, local coding conventions" better than "implicit, global code quality criteria", possibly "an inherent limitation in how LLMs model code structure" (§4.4). The only evidence is the Pylint/MI divergence.
- **Smaller diffs with lower MI** mean LLMs "optimize for the minimal changes necessary to satisfy immediate task requirements". The extra human lines go into abstraction (§4.4). This is inferred from Figs. 8–9 together. It is confounded: the human diff spans 71 commits of real work, including untested features, docs and refactors the LLM is never asked for.
- **Provider differences across γ** are said to reflect providers' training strategies (§4.2). This is labelled a conjecture.
- **Turns are not the bottleneck; capability is** (App. B.2). Evidence: weak models use most of the turns and still fail.

## 6. Recommendations (the authors')
- Shift coding evaluation "from static, short-term functional correctness toward dynamic, long-term maintainability". Use evolution-based, CI-loop benchmarks rather than snapshot ones.
- Use EvoScore with γ ≥ 1 so long-term stability is rewarded.
- Treat regression control as the open problem ("particularly in controlling regressions", §5).
- Build agents that "not only write code that works, but write code that lasts".

They make no practitioner or workflow recommendations, and do not say how to reduce regressions.

## 7. Limits
**Stated or implied by the authors:**
- The γ effects and the regression-trend explanations are conjectures.
- Python only.
- 100 tasks.

**My own:**
- **Requirements come from oracle tests, not humans.** The Architect sees the failing tests, so this is test-gap-driven development toward a known target. A real ticket is ambiguous and has no hidden oracle. Diagnosis is easier here, and "maintainability" means only "can still pass the next oracle tests".
- **EvoScore at γ=1 mostly measures progress, not maintainability.** It is the average progress over iterations, and a model that solves fast scores high whatever its structure. The maintainability reading needs γ>1, which the headline doesn't use, and only a narrow 0.8–1.2 sweep is shown. It is also unclear how iterations after an early finish are scored (presumably a(c) = 1 carried forward). That would favour fast finishers further.
- **Agents may not run tests.** This is deliberate, but it removes the self-check loop real agents (and wf) use. Regression rates are therefore probably inflated compared with an agent that runs the suite before handing off. It may also explain why the Architect/Programmer pair can't catch its own breakage.
- **No variance.** As far as stated, it is one run per model per task. Differences of a few points (e.g. 20% vs 23% zero-regression) are likely noise, given n=100 and a ±~8 pp binomial CI.
- **The MI/Pylint comparison uses solved tasks only.** The task sets differ per model (Opus 4.6 ~91 tasks, DeepSeek-V3.1 ~8), so the comparisons across models are not like for like. The MI scope is unspecified. The human oracle diff includes work outside the tested requirements, which biases the line-count and possibly the MI comparisons.
- **The changed-lines comparison is confounded.** Human: 71 real commits including untested features and refactors. LLM: only what makes the tests pass. ~10⁶-line LLM outliers go unexplained.
- **Regression rate and magnitude are undefined.** The Pearson correlations run over ≤20 iteration points with survivorship: strong models stop early, so later iterations contain only the hard, unsolved tasks.
- **Task selection.** Ranking by time span and commit count keeps the longest episodes, which are large, multi-feature evolutions (≥500 changed source lines). Dependency-unchanged spans skip the work around dependency upgrades.
- **Contamination.** These are public repos with >500 stars, and the oracle commits are probably in training data. Newer models may have seen them.
- **One harness (iFlow CLI)**, from Alibaba, the authors' affiliation; results could be harness-specific. The same model plays both roles.
- **No ablation** of the architect/programmer split, the 5-requirement cap, or the priority rules. The paper provides no evidence that its own protocol helps.
- **Model generation.** The ranking is a snapshot at March 2026. The authors themselves show fast movement (Opus 4.5 → 4.6: EvoScore +0.22, zero-regression +25 pp, turns 9.8 → 5.3).
- **"First" claim.** It overlaps with SWE-EVO, SWE-Bench-CL and LongCLI-Bench (cited in App. A).

## 9. For wf — MY INFERENCE, not the paper's

**Why it is relevant.** SWE-CI's setting is wf's long-run setting: many rounds a week, each built on code earlier agents wrote. That is the "the codebase teaches the next change" principle. The paper's claim is that what compounds is (a) regressions and (b) structural complexity that lint does not see.

**Supports:**
- **Deterministic checks between phases (`wf check`), especially the full test suite and not only the repro.** Regressions are the dominant failure: for most models >75% of tasks see one, and the best model still has one in 24% of tasks. SWE-CI agents could not run tests at all, and wf's design already avoids that weakness. The paper argues for keeping it non-negotiable: every per-commit agent's output must pass the *whole* suite, not just the repro going red→green.
- **The T2 human diff read, as the place where "shape" is owned.** The Pylint/MI split (15/20 beat humans on Pylint; 0/20 beat them on MI; GPT-5.4 best on Pylint at 72% and worst on MI at 84% losses) says lint and style gates pass code that is structurally worse. `wf standards` per-rule agents and lint confirm surface conventions. They do not confirm maintainability. That remains Shay's job at T2, which supports "don't automate away owning the code".
- **A plan phase that produces behaviour contracts with acceptance criteria, then a fresh implementer.** The Architect's `requirement.xml` (location / description / contract / acceptance, ≤5 items, no implementation) closely resembles a wf plan. The priority rules (shared low-level modules before specific cases) are a reasonable checklist for the plan agent. But the paper never tests whether the split helps, so this is a pattern, not evidence.
- **Using the strongest model rather than more retries.** Weak models use up 20 turns without finishing, and the gains come in turns 1–4. Opus 4.6 finishes in 5.3 turns on average with 91% solved. If a wf commit agent's fix loop against `wf check` hasn't converged after a few attempts, more attempts are unlikely to help, and regressions get *more frequent* in later iterations for 12/20 models. This suggests a **hard cap on fix-loop iterations, then escalate to Shay**, rather than letting an agent grind.

**Suggests adding (cheap, deterministic):**
- **An explicit regression gate in `wf check`.** Record the set of tests passing at the round's base commit. Fail if any of them fails after a commit. This is the paper's "frozen oracle report → compare" mechanism (Fig. 3) and differs from "the suite is green": it also catches a test that was skipped or deleted. The test-integrity rule ("PROHIBITED from modifying … tests") also suggests a check that agents did not edit or delete existing tests beyond what the plan names.
- **A complexity-delta measurement in validate**, reported to T2 rather than used as a gate. For example, cyclomatic complexity or MI of the touched functions before and after: radon for the FastAPI side, ESLint `complexity` for Svelte/TS. This puts the paper's one discriminating metric in front of Shay at almost no reading cost. Keep it a number in the T2 summary, not a new agent; the harness-complexity worry applies.
- **A periodic look at drift across rounds.** Agent-written code accumulating complexity is invisible per round. A weekly trend of complexity over the files rounds touched would be the wf-scale version of EvoScore. This is optional, and only worth it if per-round deltas show a pattern.

**Contradicts / cautions:**
- The paper notes that LLMs make *smaller* diffs and that this comes "at the cost of maintainability". This mildly cuts against a pure "minimal diff" norm, if wf has one. But the comparison is confounded: human diffs include untested features. For small bug fixes, minimal diffs are still right. The lesson is narrower: **a small diff that adds a special case to a complex function is the failure mode** to look for at T2, rather than "write more lines".
- Don't adopt EvoScore-style long-horizon metrics as a wf gate. At γ=1 the metric measures progress more than maintainability.

**Where it does not apply:**
- The task scale is different. SWE-CI tasks are 233-day, 71-commit, ≥500-line evolutions driven by up to 20 autonomous loops. wf rounds are small tickets with a human approving the plan (T1) and reading the diff (T2). The compounding in wf happens *across* rounds, with Shay in between, which the paper never models.
- There is no human, and requirements come from oracle tests. wf's research phase (reproduce from a ticket, red at one place over 3 runs) and the human gates have no counterpart, so the paper says nothing about them.
- The agents could not run tests. Absolute regression rates therefore overstate what a wf commit agent with `wf check` would produce. The *direction* (regressions are common; later iterations regress more) is what transfers.
- The paper covers Python libraries only. It says nothing about SvelteKit frontends, MongoDB data or UI regressions, so the before/after screenshots at T2 and wf's frontend checks are outside its evidence.
- There are no repeat runs, so it offers nothing on wf's 3-run repro-stability rule or on agent non-determinism.
- The model rankings are a March-2026 snapshot. The Opus 4.5 → 4.6 jump (+25 pp zero-regression) shows they go stale within months.
