- **Authors:** Gabriel Orlanski (corresponding), Devjeet Roy, Alexander Yun, Changho Shin, Alex Gu,
  Albert Ge, Dyah Adila, Nicholas Roberts, Frederic Sala, Aws Albarghouthi (UW–Madison, Washington
  State, MIT)
- **Date / version:** v1 25 Mar 2026; v2 7 May 2026 (the version read). arXiv cs.SE. No venue stated.
  Code and leaderboard at scbench.ai.
- **Funding:** Snorkel AI (Open Benchmarks Grants), DARPA, NSF.
- **Link:** https://arxiv.org/abs/2603.24755

## 2. Question

When a coding agent has to keep extending **its own** earlier code as the spec changes, does the
code's quality get worse, and how fast compared with human-maintained repositories? The authors also
ask whether agents can carry their own design decisions through to a full solution, and whether
quality-focused prompts stop the decline.

## 3. Method

**Benchmark.** 36 hand-written problems, 196 checkpoints (3–8 per problem). Each checkpoint is a spec
for a new feature, given in prose with embedded examples. The spec defines only external behaviour at
a CLI or API boundary (args, JSON I/O, ordering and normalization rules) and leaves the internal
structure to the agent. Running example: `code_search`, an ast-grep-like CLI in 5 checkpoints
(C1 Python exact/regex → C2 JS and C++ → C3 AST patterns with metavariables → C4 selector rules and
auto-fix → C5 Go/Rust/Java). Problems include cfgpipe, circuit_eval, database_migration,
file_query_tool (SQL), forge, mocked_http, test_translator, textdrop and others (Tables 4–5 list the
design decisions each one stresses).
- **Design principles (§2.1):** (1) no prescribed internal interfaces; (2) **no visible test suite**:
  the agent sees only the spec and its examples, never the tests or their results; (3) black-box and
  language-agnostic. Only the Python track was evaluated, because of cost.
- **Task formulation (§2.2):** y_i = π(x_i, y_{i−1}). The agent gets the new spec and its own previous
  workspace, **without the earlier conversation**, so it has to reason from the code alone. The
  workspace is never replaced by a reference solution, so early design choices carry forward.
- **Problem construction:** written by the authors. Each problem was reviewed by at least one other
  author. Problems that "frontier agents could solve in a single shot" or that did not test design
  were dropped. Tests were refined by running an agent against each checkpoint.

**Tests (§2.4).** Four categories: Core (behaviour in the spec), Error (failure modes), Functionality
(hidden, exhaustive) and Regression (all earlier checkpoints' tests). They give these measures:
- **Strict:** a checkpoint counts only if all of its tests pass, including regression.
- **Isolated (ISO):** all non-regression tests for that checkpoint pass.
- **Core:** only the core tests pass.
- **Partial:** a problem with at least one checkpoint solved strictly.

When an agent crashes, the checkpoints it did not reach score 0 for correctness and are left out of the
quality metrics.

**Quality metrics (§2.3).**
- **Structural erosion.** For each callable f, mass(f) = CC(f) × √SLOC(f). Erosion is the share of the
  total mass held by functions with CC > 10 (the Radon threshold). Range [0,1].
- **Verbosity.** |lines flagged by any of 137 hand-built ast-grep rules ∪ clone (structural
  duplicate) lines| / LOC. Range [0,1]. The rules came from "observed cases of verbose code, best
  practices, and commonly cited anti-patterns on social media."
- The authors argue for keeping two separate metrics over a composite such as the Maintainability
  Index: code can bloat without concentrating complexity, and the reverse.

**Agents and setup (§3, App. C).**
- 15 models from six providers: Opus 4.5/4.6/4.7, Sonnet 4.6, GPT 5.2 Codex, 5.3 Codex, 5.3 Spark,
  5.4, 5.4 Mini, 5.5, Cursor Composer 2, GLM 5.1, Kimi K2.5/K2.6, MiniMax M2.7.
- They ran in their native harnesses, headless: Claude Code (2.0.51–2.1.111), Codex CLI
  (0.93.0–0.124.0), Cursor CLI, Kimi CLI, plus OpenCode for some extra runs. Reasoning effort was high
  where the harness allows it.
- Each checkpoint ran in a fresh Docker container as a non-root user. Only the working directory
  persisted; installed packages, shell history and agent session data were reset.
- Limits: 2 h wall clock per checkpoint, no turn cap, no cost cap.
- Baseline prompt `just-solve`: "Implement a program that 100% solves the specification. That is all
  you need to do." It also asks for a venv and requirements.txt.
- Trajectories are mapped to five progress phases (Start, Early, Mid, Late, Final) so that problems of
  different lengths can be compared.
- Apparently one run per configuration. Table 1 reports each model's "best just-solve run", and
  Table 8 lists 26 runs across harnesses and prompts. No seeds and no confidence intervals on solve
  rates.

**Human baseline (§3.3, App. D.1).**
- 473 Python repositories in four GitHub-star tiers: Hobby <100 (n=114), Niche 100–1k (124),
  Established 1k–10k (120), Major ≥10k (115).
- Up to 30 source-modifying commits sampled per repository: 13,667 commits spanning 1990–2026.
- The HEAD commit is used for the cross-sectional comparison, and the commit sequence is treated as
  the counterpart of an agent trajectory.

**Prompt study (§3.4).**
- `anti-slop` (Listing 9): "No god functions/classes". It also asks to keep defensive checks,
  single-use variables, comments a human wouldn't add, trivial wrappers, heavy nesting, if/else ladders
  and "a ton of helper methods" to a minimum, and to group functions into files.
- `plan-first` (Listing 10): plan, write the simple solution, make it 100% correct, then refactor, plus
  the same style rules.
- Tested on GPT 5.3 Codex, GPT 5.4 and GPT 5.5. One anti-slop run on MiniMax M2.7 appears in Table 8.

## 4. Results

**Correctness (§3.1, Table 1, Fig. 2).**
- No run fully solves any of the 36 problems end to end.
- Best strict solve rate: GPT 5.5 at 14.8%. Best isolated: GPT 5.5 at 28.1%. Best core: 67.3%. The
  text credits Opus 4.5, but Table 1 shows Opus 4.5 at 57.7% and Opus 4.6 at 67.3%, so the text looks
  wrong.
- Strict / Iso / Core / Partial by model:

  | Model | Strict | Iso | Core | Partial |
  |---|---|---|---|---|
  | GPT 5.3 Codex | 11.2 | 26.0 | 60.7 | 41.7 |
  | GPT 5.4 | 10.7 | 23.5 | 62.8 | 36.1 |
  | Opus 4.7 | 8.2 | 20.9 | 65.8 | 36.1 |
  | Sonnet 4.6 | 7.1 | 16.8 | 57.7 | 27.8 |
  | MiniMax M2.7 | 2.0 | 4.1 | 28.1 | 8.3 |
  | GPT 5.5 | 14.8 | 28.1 | 66.8 | 50.0 |

- Cost per checkpoint ranges from $0.20 (GPT 5.3 Spark) to $3.17 (Opus 4.6). Net cost per model
  ranges from $37 to $621.
- Over the course of a problem:
  - The gap between core and isolated pass rates widens from 2.5× to 5.4×.
  - Core pass rate falls from 64.6% to 35.5%.
  - The Functionality pass rate barely moves (62.7% → 57.7%).
  - The Error pass rate falls from 80.1% to 62.2%. Error handling decays first.
- Mean cost per checkpoint grows 2.2× from start to end, while the mean share of lines changed falls
  from 97.4% early to 29.5% late. Agents spend more but move less code.
- 13.18B tokens in total. Normalized to 196 checkpoints, Composer 2 used 0.38B and Kimi K2.6 1.14B.

**Degradation within a trajectory (§3.2, Fig. 3).**
- Erosion rises in **77%** of trajectories and verbosity in **75.5%**.
- The mean number of functions with CC ≥ 10 rises from 3.6 to 23.7. The mean maximum CC rises from
  27.5 to 69.0.
- Mean quality metrics per model run fall in narrow bands: erosion 0.49–0.76, verbosity 0.32–0.51.
  The best are GPT 5.5 (0.49/0.32) and GPT 5.4 (0.51/0.33). Model generation changes the level only
  modestly, and the Claude models are at 0.70–0.76 erosion.
- Structural duplication grows 96% while AST-grep violation density grows only 0.3%. The verbosity
  growth comes from rewriting and copying existing code, not from new idiom-level smells.
- Case study (App. B.2): Opus 4.7's `forge` `main()` goes from CC 13 to CC 92 and from 38 to 240
  lines over 8 checkpoints, monotonically. argparse is replaced by a hand-written flag loop in which
  seven flags each get an identical pair of `--X val` / `--X=val` branches, with no helper extracted.
  `code_search`'s `find_matches_in_file()` reaches 117 lines at C5, holding nearly all the
  decision-point mass.

**Versus human repositories (§3.3, Table 2, Fig. 4, App. D).**

| Group | n | Verbosity | Erosion |
|---|---|---|---|
| Human panel | 473 | 0.19 ± 0.11 | 0.34 ± 0.22 |
| Agent checkpoints | 2869 | 0.44 ± 0.18 | 0.68 ± 0.20 |

- Agent code is **2.3× more verbose and 2.0× more eroded**. Star tier barely matters: Major repos sit
  at 0.19/0.37 and Hobby at 0.21/0.33.
- Only 18 of 473 repos exceed the agent verbosity mean. Examples: huggingface/transformers
  (0.451/0.473, from per-architecture file duplication) and fastapi (0.273/0.219). Flask (0.111/0.209)
  and scikit-learn (0.094/0.407) are low.
- Slope per checkpoint, agent vs human median: verbosity 0.0144 vs 0.0022 (~6.6–7×) and erosion
  0.0264 vs 0.0053 (~5×).
- Erosion rises in 77% of agent trajectories vs 53% of human repos (103/196 repos with ≥5 commits).
  Human verbosity rises in 68% of repos (256/378), with a median first-to-last growth of 36%. Humans
  degrade too, just more slowly.
- Effect of the agent era on human repos:
  - Pre- vs post-ChatGPT median verbosity: 0.155 vs 0.166.
  - Split at January 2024: verbosity 0.156 vs 0.168, erosion 0.278 vs 0.319.
  - Within the 321 repos that have data on both sides, the median shift is +0.002 verbosity and +0.014
    erosion. 55% of those repos are more verbose afterwards and 59% more eroded. That is small but in
    the "slop" direction.

**Prompting (§3.4, Table 3, Fig. 5).**
- anti-slop lowers verbosity by 27.5% (GPT 5.4), 35.6% (GPT 5.5) and 32.8% (GPT 5.3 Codex), and
  erosion by 45.1%, 57.6% and 34.3%. In absolute terms, GPT 5.5's erosion goes from 0.49 to 0.21 and
  its verbosity from 0.32 to 0.21.
- The **slope does not change**: the "average quality velocity remains 1.3 percentage points per
  checkpoint". Only GPT 5.4 with anti-slop improves from start to end.
- Correctness cost: strict solve rate drops by an average of 2.4 pp for anti-slop and 3.6 pp for
  plan-first. The worst case is GPT 5.5: strict 14.8 → 9.2 with anti-slop and → 8.2 with plan-first.
  Core improves 0.8 pp under plan-first.
- Cost per checkpoint rises 12.1% on average. GPT 5.4 with anti-slop goes from $0.72 to $0.90.
- plan-first, which asks the agent to plan before coding, reduces erosion less than anti-slop does
  (GPT 5.5: 0.29 vs 0.21) and costs the most strict correctness.

**Sensitivity of the erosion metric (App. B.3, Table 6). This is a negative result the text plays
down.**
- Across 9 variants (CC cutoff 8/10/12 × size term), erosion's correlation with the **next
  checkpoint's pass rate is ≈0** (reported metric −0.018; best variant −0.136). Its correlation with
  next-checkpoint cost is positive but weak (+0.167).
- Plain LOC predicts both better: −0.212 for pass rate and +0.502 for cost. Max CC: −0.117 and +0.356.
- The paper does **not** show that erosion or verbosity cause later failures. What it shows is that
  they rise, and that they track cost weakly.

**Harness effect (Table 8).** The same model in a different harness gives very different results.
GLM 5.1 reaches core 40.3% in Claude Code but 20.4% in OpenCode. Kimi K2.5 reaches core 39.8% in Kimi
CLI, 31.6% in OpenCode and 29.6% in Claude Code.

**Internal inconsistencies noticed:**
- The core-rate leader is misattributed (see above).
- Verbosity growth is "6.6×" in the intro and "roughly 7×" in §3.3.
- Erosion reduction is "up to 62.3%" in RQ4 but at most 57.6% in the text.
- The strict drop is "2.3 pp" in the intro and abstract but 2.4 pp in §3.4.
- Table 7 (harness versions) omits Opus 4.7 and GPT 5.5, which appear in Table 8.

## 5. Mechanisms (authors' account and evidence)

- **Patching instead of restructuring.** "Agents under iteration tend to patch new logic into
  existing functions rather than distributing it across focused callables." Evidence:
  - The number of high-CC functions and the maximum CC both grow.
  - The `forge` `main()` and `find_matches_in_file()` case studies.
  - The share of lines changed falls from 97.4% to 29.5% while cost rises 2.2×. Late checkpoints are
    local edits to a structure that keeps growing.
- **Compounding early decisions.** Because the workspace carries forward, "local shortcuts compound"
  (Fig. 1 example: correctness 1.00 → 0.10). A design that hardcodes one language at C1 forces
  cascading rewrites at C2 and C5. Evidence: the illustrative running example and the declining
  strict and core rates. There is no causal test.
- **Copying, not new smells.** Duplication grows 96% vs +0.3% for rule violations, so verbosity growth
  comes from duplicating existing code.
- **Tests do not see it.** Pass rates and quality are scored separately, and the quality metrics are
  withheld from the agent. "pass rates can remain stable even as the underlying code becomes harder to
  extend". This is supported by the near-zero erosion→pass correlation, which also cuts against any
  claim that slop causes the failures.
- **Prompts change the level, not the dynamics.** Instructions improve the starting quality, but
  iteration re-erodes the code at the same rate. The authors offer no deeper explanation.
- The authors do not explain why error-handling tests decay fastest. Hidden error tests together with
  growing ad-hoc branches is my guess, not theirs.

## 6. Recommendations

The paper is mostly diagnostic. Its explicit recommendations are few:
- Benchmarks should evaluate **iteratively**, with agents building on their own code, hidden tests,
  black-box contracts and no prescribed internals. Single-shot pass rates hide degradation.
- Track quality (erosion, verbosity) separately from correctness and at every checkpoint, rather than
  through one composite maintainability score.
- Prompting is not enough: "prompting strategies trade capabilities for better initial quality, with
  little impact on the iterative degradation". By implication, something other than instructions is
  needed. They do not test tool-based quality feedback, refactor passes, reviewers or linters in the
  loop.

## 7. Limits

**Stated by the authors:**
- Python track only, because of cost.
- Problems are author-written.
- Harness versions vary by model.
- Failed checkpoints are excluded from the quality metrics.
- The human comparison is "calibration", not a matched experiment.

**Mine:**
- **No feedback loop at all.** The agent never sees the tests (or their results) or the quality
  metrics, and has no reviewer. Real workflows, wf included, have visible tests, lint and review. The
  benchmark measures unaided self-extension.
- **No conversation memory between checkpoints, and a minimal prompt** ("That is all you need to
  do"). The agent has no instruction to keep the code maintainable and no project rules file.
- **Big steps.** Each checkpoint is a sizeable feature (97% of lines changed early), in a greenfield
  program the agent itself wrote. That is very different from small bug fixes in a large mixed
  human/agent codebase.
- **Mismatched units in the human comparison.**
  - One human "checkpoint" is a sampled commit, with up to 30 sampled across years, so one step spans
    many real commits. One agent checkpoint is one feature.
  - The comparison sets whole mature repos (HEAD) against small fresh CLI programs. Size and domain
    differ, and erosion as a share of mass behaves differently in small codebases.
  - The "7× / 5× faster" claim is therefore loose.
- **Possible bias in the verbosity rules toward agent style.** The 137 ast-grep rules were written from
  observed agent verbosity and social-media anti-patterns. The clone component, though, is neutral.
- **The metrics do not predict outcomes.** Erosion does not predict next-checkpoint pass rate (−0.018)
  and predicts cost only weakly. LOC is the better predictor. "Slop" is shown to grow, not shown to
  hurt within this horizon.
- **Thin statistics.** Apparently a single run per configuration, no seeds, no CIs on solve rates, and
  no significance tests reported despite the word "significantly". The prompt study covers 3 models,
  all OpenAI.
- **Selection.** Problems a frontier agent one-shots were removed, which biases the benchmark toward
  hard ones, consistent with the 14.8% ceiling.
- Several numbers disagree between sections (see §4). Read headline figures with ±1 in mind.
- **Model generations.** The models are early-to-mid 2026, so the results are current, but the levels
  (not the slopes) move with each model. GPT 5.5 has erosion 0.49 vs 0.73 for GPT 5.2 Codex.
- **Industry funding** (Snorkel AI) for a benchmark paper. That is a minor concern.

## 9. For wf (my inference, not the paper's)

**Why it is relevant.** wf's setup is the paper's setup at a smaller grain. Fresh-context agents (no
memory of the previous round) extend a codebase that earlier agents wrote, many rounds a week. "The
codebase teaches the next change" is exactly the mechanism by which the paper's degradation
compounds. Patched-in branches and copied blocks become the example the next agent copies. Duplication
grew 96% while new rule violations grew 0.3%, which says agents copy what is there.

**What it supports in wf:**
- **"Verification beats instruction."** This is the paper's strongest practical result. A carefully
  written anti-slop prompt lowered the starting level by a third to a half but left the slope (~1.3 pp
  per checkpoint) unchanged. It also cost 2.4 pp strict correctness and 12% more spend.
  - Do not expect better phase prompts or longer AGENTS.md style rules to hold the codebase's shape
    over many rounds.
  - Note what the paper never tested: per-rule reviewers (`wf standards`), a critic, deterministic
    checks and human diff review. Those are wf's actual mechanisms. The paper shows only that the
    no-feedback, prompt-only version fails.
- **T2, where Shay reads the diff and owns the shape.** The paper shows that tests going green do not
  reveal the decay. Functionality pass rates moved under 6 points while erosion and verbosity climbed.
  A red→green repro plus lint, typecheck and tests (`wf check`) will pass a round that grew a god
  function. The human diff read is currently the only wf gate that sees structure.
  - Because human attention is scarce, it should be backed by a number (see below).
- **Fresh context per phase is not, by itself, a cause of decay.** The paper's agents also lacked prior
  context. The decay comes from building on uncorrected own output without feedback, so per-phase fresh
  context is fine as long as the quality signal is external.

**What it suggests adding (deterministic, cheap; "feedback given twice becomes infrastructure"):**
- **A structure ratchet in `wf check`, computed on the files a round touches, before vs after:**
  - The number of functions with CC > 10, and any function crossing that threshold. Radon/ruff `C901`
    for the FastAPI backend; ESLint `complexity` for the TypeScript/Svelte frontends.
  - The maximum CC in touched files.
  - The new clone lines the diff introduces (a duplicate-code detector such as jscpd, scoped to the
    diff).

  Report the deltas at T2 next to the before/after screenshots, or fail when a touched function
  crosses the threshold without a note in the plan.
  - This turns the paper's metrics into a gate and fits "make the environment deterministic".
  - Keep it to a delta on touched code, not a whole-repo score, to stay small. The worry about the
    harness growing complex applies.
- **Plan phase / T1: name where the new logic lives.** Say whether it extends an existing function or
  gets a new one, and why. The failure mode in the paper is silently patching branches into
  `main()`-like functions. Shay approving that decision at T1 is cheaper than spotting it in the diff.
- **A tension to surface.** wf's "surgical changes / touch only what you must" norm pushes agents
  toward exactly the in-place patching that concentrates complexity. That is how `forge` `main()`
  went from 38 to 240 lines. A rule along the lines of "surgical at the module level, but extract
  rather than add a fourth branch to an already-complex function" would reconcile the two. The ratchet
  above is what makes it enforceable.
- **Periodic, separately-ticketed refactor rounds** for the hottest functions, driven by the same
  metric. The paper's human repos degrade too, at 53–68%, so some decay is normal. What matters is the
  slope, and refactoring is how humans keep it down.
- **The paper argues against folding "plan first, then refactor" into the coding agent's prompt.**
  plan-first lowered strict correctness by 3.6 pp on average. wf already separates the plan into its
  own phase with human approval, which is a different and untested intervention. Do not read the
  paper as evidence against wf's plan phase, only against self-planning by prompt.

**Where the paper does NOT apply to wf:**
- **Step size.** SCBench checkpoints are large feature extensions to a small greenfield CLI (97% of
  lines touched early). wf rounds are mostly small fixes in a large existing app, where per-round
  structural change is smaller and the degradation slope per round should be much lower. The 77% /
  2× numbers cannot be transferred to rounds.
- **Feedback.** SCBench agents get no tests, no test feedback, no lint, no reviewer and no human. wf
  has all of these. The paper measures the worst case of unaided self-extension, not a gated workflow.
- **Language and stack.** The paper covers Python CLIs and APIs only. JewelryX's Svelte/TypeScript
  frontends are outside its evidence. The Python/FastAPI backend is closer, but it is a web service
  with MongoDB, not a CLI.
- **The metrics don't predict failure.** Erosion did not predict next-checkpoint pass rate, and LOC
  predicted cost better. If wf adds a check, a touched-file LOC delta plus a CC-threshold crossing is
  as defensible as the paper's composite erosion score, and simpler. Do not adopt the exact erosion
  formula as if it were validated.
- **Model levels.** The levels differ by model (GPT 5.5 erosion 0.49 vs Opus 4.7 0.76), so the absolute
  numbers depend on whichever model wf uses. Only the "it rises unless corrected" direction is robust
  across all 15 models.
