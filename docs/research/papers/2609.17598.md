# 2609.17598 — Not All Agents Are Equal

## 1. Citation
- **Title:** Not All Agents Are Equal: Code Quality and Post-Merge Maintenance Across Five Autonomous Coding Agents in the Wild
- **Author:** Obada Kraishan (single author), College of Media and Communication, Texas Tech University, Lubbock, TX
- **Date / version:** v1, submitted 12 Sep 2026 (only version). arXiv cs.SE. 9 pages, 5 figures, 2 tables.
- **Venue:** none stated (preprint).
- **Link:** https://arxiv.org/abs/2609.17598 (read in full from https://arxiv.org/html/2609.17598; the paper has no appendices)

## 2. Question
What happens to code that autonomous coding agents get merged into real public repositories: is it
more defect-prone, less maintainable, more often reworked or reverted, and differently reviewed than
human code in the same repositories? And do those outcomes differ between agent products (vendors)
rather than between "agents" and "humans" as a whole? Five RQs: RQ1 defect-prone patterns, RQ2
maintainability, RQ3 post-merge maintenance overhead (churn, reverts), RQ4 vulnerability classes,
RQ5 human review behaviour.

## 3. Method
**Corpus (§3.1, Table 1).** The curated slice of the AIDev dataset (Li, Zhang, Hassan, MSR 2026;
agentic PRs in repos with >100 stars). 33,596 agent PRs labelled by vendor: OpenAI Codex, Devin,
GitHub Copilot (the agent, not autocomplete), Cursor, Claude Code. Plus a human baseline built from
AIDev's human PR sample: kept only human PRs from repos that also contain agent PRs (810 repos),
restricted to the agents' window (24 Dec 2024 – 30 Jul 2025), capped per repo with a fixed seed.
Result: 4,027 human PRs alongside 9,750 agent PRs in those same 810 repos; the rest of the agent PRs
(2,807 repos total) are kept "for additional within-agent power". Total 37,623 PRs.
**No underlying model names or versions are given** for any agent, and nothing about how the agents
were configured or prompted, or what harness they ran in.

Table 1 (PRs / merged / enriched / statically analysed / median changed lines):

| Group | PRs | Merged | Enrich. | Anal. | Med. lines |
|---|---|---|---|---|---|
| OpenAI Codex | 21,799 | 18,004 | 17,761 | 4,570 | 63 |
| Devin | 4,827 | 2,595 | 2,186 | 1,224 | 61 |
| GitHub Copilot | 4,970 | 2,139 | 3,459 | 1,102 | 76 |
| Cursor | 1,541 | 1,005 | 946 | 571 | 96 |
| Claude Code | 459 | 271 | 456 | 241 | 495 |
| Human | 4,027 | 3,076 | 3,038 | 1,225 | 52 |
| Total | 37,623 | 27,090 | 27,846 | 8,933 | |

Codex is 58% of agent PRs; Claude Code only 459 PRs (241 analysed, 267 in revert analysis).

**GitHub enrichment (§3.2).** For each PR, the changed-file list via the REST API; for merged PRs,
commits touching the PR's **most-changed file** in the 90 days after merge. Revert-style commits are
flagged **by commit message**. 58,792 cached API responses. 30,721 PRs submitted, 29,730 (96.8%)
succeeded; 991 (3.2%) deleted or blocked repos/PRs, reported not imputed. (Note: Table 1's "Enrich."
column sums to 27,846, not 29,730; the paper does not reconcile this.)

**Static analysis (§3.3).** Only added lines of each diff, only Python, JavaScript, TypeScript:
8,933 PRs, 1,348,822 added lines (23.7% of PRs). Diffs >5,000 added lines excluded as auto-generated.
- Maintainability counts: TODO/FIXME markers, lines >120 chars, comment lines, branching keywords,
  maximum indentation depth.
- Security smells: a regex catalog mapped to 8 CWE classes: hardcoded credentials (CWE-798), SQL
  string construction in query calls (CWE-89), shell injection (CWE-78), eval/exec (CWE-95), unsafe
  deserialization (CWE-502), weak hash/cipher (CWE-327), DOM XSS sinks (CWE-79), concatenated paths
  in file-open (CWE-22). Treated as "smells", not confirmed vulnerabilities.
- Densities per 100 added lines: s_i = 100·S_i/L_i (security hits), m_i = 100·M_i/L_i
  (maintainability hits).
- Churn for merged PR: c_i = 100·F_i/C_i, F_i = follow-up commits on the most-changed file within 90
  days, C_i = changed lines.

**Review measures (§3.4).** From AIDev review/comment/timeline tables, **which exist only for agent
PRs**, so RQ5 compares agents with each other, not with humans. Bot reviews counted separately;
latency = PR creation → first human review.

**Statistics (§3.5).** Non-parametric: Mann–Whitney U with Cliff's δ (|δ|<.147 negligible, <.33
small, <.474 medium, else large); Kruskal–Wallis H with ε² across the six groups, Dunn's test for
pairs; χ²/Fisher with odds ratios and 95% CIs for binary outcomes; Benjamini–Hochberg FDR 0.05 within
each family; bootstrap CIs for δ (5,000 resamples, fixed seed). A "validation gate" checks schema,
ranges and group coverage before analysis; 63-variable codebook. δ>0 means agent larger than human.

## 4. Results
**RQ1: defect-prone patterns (§4.1, Fig. 2).**
- Security-smell *density* differs across groups (H(5)=52.5, p<.001, ε²=.005) but every pairwise
  effect vs humans is **negligible**: Codex δ=−.02 (p=.001), Copilot δ=−.02 (p=.025), Cursor δ=−.03
  (p=.004), Devin n.s. (p=.60), Claude Code δ=+.05 (p=.004). Author's summary: per-line smell density
  is similar across authorship.
- *Presence* (any security smell in the PR): pooled agents **2.9% vs humans 4.6%**, χ²(1)=8.59,
  p=.003, **OR 0.63 [0.47, 0.85]**. Per group: Cursor 1.6%, Codex 2.5% cleanest; **Claude Code 9.5%**,
  about twice the human rate (outlier).
- Maintainability-smell density separates more (H(5)=467.7, ε²=.052): Codex has fewer TODOs and long
  lines than humans (δ=−.19, small), Devin somewhat fewer (δ=−.07), others at human level.
- Size-stratified check: the pooled agent–human security-density difference is concentrated in the
  largest PRs (XL bucket δ=−.08, p=.025); no difference in the four smaller buckets.

**RQ2: maintainability (§4.2).** All four structural measures differ (all p<.001): nesting H=118.3
ε²=.013; branch density H=104.0 ε²=.011; **comment ratio H=868.5 ε²=.097** (largest); maintainability
smell density H=467.7 ε²=.052. Median comment ratio: Copilot .065, Claude Code .076, Cursor .042;
**median Codex, Devin and human diffs contain zero comment lines**. Claude Code writes the heaviest
structure (median nesting 4 vs 3 elsewhere; highest branch density .063/line), consistent with its
median 495-line PRs. 44 of 60 Dunn pairwise tests significant; every agent differs from at least two
others on at least one measure; no agent dominates all four.

**RQ3: post-merge maintenance (§4.3, Table 2, Fig. 3).** 26,283 merged PRs with a full 90-day window.
- Raw follow-up commits: Copilot files see the least later activity of any group (δ=−.20 vs humans,
  small, p<.001); Cursor, Claude Code below humans (negligible); Codex slightly above (δ=+.03, p=.020).
- Churn per changed line: **Claude Code lowest (δ=−.33, medium, p<.001; median c=0.5 vs 5.3 for
  humans)**, then Copilot (δ=−.16), Cursor (δ=−.08); Codex and Devin at human level.
- Reverts within 90 days, vs human baseline **11.5%** (Table 2):

| Agent | n | Reverted | OR [95% CI] | p (BH) |
|---|---|---|---|---|
| OpenAI Codex | 17,756 | 6.1% | 0.50 [0.44, 0.57] | <.001 |
| Devin | 2,185 | 14.5% | 1.31 [1.11, 1.54] | .004 |
| GitHub Copilot | 2,094 | 12.5% | 1.10 [0.93, 1.31] | .457 |
| Cursor | 946 | 11.4% | 1.00 [0.79, 1.25] | 1.00 |
| Claude Code | 267 | 10.5% | 0.90 [0.60, 1.36] | .878 |

  Only Codex (better) and Devin (worse) differ from humans. Author: no agent imposes a measurably
  higher per-line maintenance burden than humans.

**RQ4: vulnerability classes (§4.4, Fig. 4).** Under-represented in pooled agent code after
correction: hardcoded credentials CWE-798 (**0.9% vs 2.2%, OR 0.39 [0.25, 0.62], p<.001**) and
eval/exec CWE-95 (0.2% vs 0.8%, OR 0.25 [0.11, 0.56], p=.006). No class over-represented; weak crypto
and XSS lean that way but don't survive correction and rest on small counts. Per agent: **Claude Code
has the highest hardcoded-credential smell rate, 3.3%** of analysed PRs (above human 2.2%); Codex and
Cursor 0.5% each: a fourfold spread on one class. (With 241 analysed Claude Code PRs, 3.3% ≈ 8 PRs
and 9.5% ≈ 23 PRs; my arithmetic.)

**RQ5: human review (§4.5, Fig. 5).** Agents only; review coverage 5.4% (Codex) to 51.2% (Copilot) of
each group's PRs. All measures differ (p<.001): hours to first human review H(4)=88.9 ε²=.014; human
reviews/PR H=700.6 ε²=.116; change requests H=293.0 ε²=.048; issue comments H=243.0 ε²=.049; bot
reviews H=541.0 ε²=.119. **Copilot: 3.6 human reviews and 0.43 change requests per PR on average, plus
the most bot reviews (4.0).** **Claude Code: median 12.6 h to first human review vs 1–4 h elsewhere**,
plausibly because its PRs are an order of magnitude larger. Devin and Codex PRs usually get one or two
quick human reviews.

**Surprising / negative findings.** The feared technical-debt and churn explosion (GitClear 2024)
does not show on these measures within 90 days. Agent code is pooled-cleaner on security smells.
Per-line smell density barely differs at all (all δ negligible). Vendor gaps exceed agent–human gaps.

## 5. Mechanisms (as the authors give them)
- **Why agents look as good as or better than humans:** two candidate mechanisms that the design
  "cannot separate": (a) agents write conservative, template-like code; (b) humans steering them assign
  bounded, well-specified tasks (§5). No direct evidence for either; task mix is unobserved.
- **Why Claude Code stands out (more smells, heavier structure, slower review, lowest per-line
  churn):** PR size, about 8× the other groups' median. Per-line densities and the size buckets
  "limit, but cannot remove" the confound (§5).
- **Copilot's heavy review:** it is the agent most tightly integrated into GitHub's review surface
  (§4.5). Asserted, not tested.
- **Vendor heterogeneity itself:** observed, not explained; repositories and users self-select which
  agent to use and for what (§6), so it mixes product quality with task assignment.

## 6. Recommendations (the authors')
- Do not treat "AI-generated code" as one category in studies or procurement; vendor identity is the
  variable that matters, and pooling "will average away exactly the differences a maintainer cares
  about" (§5).
- "Which agent" is now a measurable engineering decision; keep measuring with the released pipeline
  as products evolve (§7).
- Human review capacity is becoming the bottleneck; research should go to **routing and prioritizing
  agent PRs**, not only generating them (§5).
- Future work: per-task context to separate agent capability from task assignment; windows longer
  than 90 days; track whether review capacity keeps pace with agent volume (§7).

## 7. Limits
**Stated by the author (§6):**
- Regex smells on diff lines flag patterns, not exploitable vulnerabilities; an upper bound. The
  catalog was validated on planted-defect patches; one path-traversal detector matched relative
  imports and inflated that class ~150×, then was fixed.
- Churn uses only the most-changed file (proxy for the whole PR); revert detection by commit message
  misses silent rewrites.
- Non-random assignment: agent choice and task mix are self-selected; the matched baseline and size
  buckets reduce but don't remove confounding.
- External validity: public >100-star repos, three languages, Dec 2024–Jul 2025, Codex 58% of agent
  PRs, Claude Code only 459 PRs; may not transfer to private code, other languages, later versions.
- Static coverage 23.7% of PRs; review coverage agents only, 5–51% by group.

**My own:**
- **Agent generations are stale.** The data ends July 2025, and the paper names no model behind any
  product. Vendor rankings describe 2025 product/model/user-population bundles, not current agents.
- **The revert measure is loose.** An 11.5% human "revert" rate within 90 days is high. Because
  detection is any revert-style commit message on the PR's most-changed file, it likely counts
  reverts of *other* changes to that file. This is a construct problem the paper does not discuss.
- **Per-line churn is biased by PR size.** c = F/C with C in the denominator. Claude Code's 495-line
  median PRs mechanically produce low churn per line, so its "lowest churn" (δ=−.33) is largely the
  size confound the author flags elsewhere.
- **Correctness isn't measured.** No tests, no bug-linked fixes, no issue reopenings. "Quality" here
  means regex smells, style counts, follow-up commits and reverts.
- **Selection by merge and survivorship.** Static analysis covers what reached the repo. Maintenance
  covers merged PRs only. Rejected agent PRs (e.g. Devin's 2,595/4,827 merged) are invisible.
- **Unclear baseline.** It is unclear whether the agent-vs-human tests use only the 9,750 matched
  agent PRs or all agent PRs across 2,807 repos. The text suggests the extra PRs add "within-agent
  power", but pooled comparisons may span unmatched repos.
- **Effect sizes are tiny.** Omnibus ε² values are mostly .005–.05. The headline significant results
  rest on large n.
- **Small counts on the key findings.** The Claude Code findings rest on tens of PRs.
- **Unreconciled numbers.** Enrichment success is 29,730 in §3.2 but 27,846 in Table 1.
- **No harness or process variables.** There is nothing on whether PRs came from a structured
  workflow (plan, tests, review agents) or one-shot delegation. The question "does process change
  outcomes" is out of scope.
- Single-author, unreviewed preprint. Python/JS/TS only, so Svelte templates are not covered.
  NoSQL/Mongo injection is not in the CWE catalog.

## 8. Quotes
- "code quality and maintenance outcomes differ more between agents than between agents and humans on several measures." (§1, contributions)
- "All five effects are negligible by the conventional bands, so the honest summary is that per-line smell density is similar across authorship once a PR reaches a public repository." (§4.1)
- "No single agent dominates all four dimensions, which argues against treating “agent code” as one population." (§4.2)
- "none of the five agents imposes a measurably higher per-line maintenance burden than human contributors in the same repositories, and two of them differ from humans in opposite directions on the most severe outcome." (§4.3)
- "agents may write conservative, template-like code, and the humans steering them may assign bounded, well-specified tasks." (§5)
- "Size is the confound to watch." (§5)
- "As agent volume grows, the scarce resource in this loop is human attention, which argues for research on routing and prioritizing agent PRs rather than only on generating them." (§5)
- "Agents are not randomly assigned to tasks." (§6)

## 9. For wf: MY INFERENCE, not the paper's
**Supports:**
- **Small, bounded rounds and "one agent per commit".** The paper's leading candidate for why agent
  code holds up is "bounded, well-specified tasks". Its clearest negative signal (Claude Code: 9.5%
  smell presence, deepest nesting, 12.6 h to first review) co-occurs with 495-line PRs, about 8× the
  others. Both point the same way as wf's research → plan → T1 scoping and per-commit agents. A
  concrete addition: put a **diff-size budget** in `wf check`, or show it at T2 (changed lines per
  commit and per round, flagged above a threshold). It costs one number, and it protects T2, which the
  paper names as the bottleneck ("the scarce resource … is human attention").
- **T2 as the scarce resource.** Copilot PRs drew 3.6 human reviews each, and bot reviews outnumber
  human ones for some agents. That supports wf's design: deterministic checks, the critic and
  per-rule `wf standards` agents absorb review, and Shay reads one diff once. It argues against adding
  more human touchpoints.
- **Verification beats instruction, for cheap security classes.** In pooled agent code, the only
  significant CWE differences are credentials and eval. Within those, Claude Code was the worst
  product on hardcoded credentials (3.3% vs 0.5% for others). A deterministic secret/eval grep in
  `wf check` costs little and fits "make the environment deterministic". For JewelryX that means
  secrets in Python/TS, `eval`/`exec`, Svelte `{@html}` (CWE-79), and raw string-built Mongo queries.
  The last two are not in the paper's catalog. The evidence is weak: tens of PRs, regex smells,
  negligible densities. So add this only as a cheap check, not as a new phase or agent.

**Suggests adding (lightweight):**
- **A post-merge measure of wf's own output.** This is the paper's actual method, and it maps
  directly onto "the codebase teaches the next change". wf can't see whether its merged rounds get
  reworked later. One script could count, per merged round, the follow-up fix/revert commits on the
  touched files within 30–90 days. It would compare against Shay's pre-wf history in the same repo
  (the paper's matched in-repo baseline idea) and show whether agent-on-agent code compounds. Use the
  paper's lessons on construct: match reverts to the actual merge SHA, not by message on a file, and
  don't normalise churn by size. Keep it a periodic report, not a gate, given the worry about harness
  complexity.
- **A comment policy as a standards rule, not a hope.** Comment ratio was the widest gap between
  products (ε²=.097; some agents comment, others write none). wf's style ("comments say why") is
  exactly the kind of variable that differs by agent/model. If it matters in JewelryX, it belongs in
  `wf standards`, where it is checked, not left to the model's defaults.

**Contradicts / cautions:**
- **Model or vendor choice.** The paper says "which agent" matters more than agent-vs-human. That
  might tempt per-phase model swaps in wf. Its rankings, though, confound product, user population and
  task mix, and they come from 2025 versions with no model names. They give no basis for choosing
  models in wf. The practical lesson: if wf changes the model behind a phase, measure the before and
  after on wf's own rounds, as with the post-merge script above. Don't import these rankings.
- The "debt hasn't materialized" reassurance comes from 90 days, >100-star public repos, and mostly
  single PRs. It does not test wf's real risk: many rounds per week, each built on earlier
  agent-written code. Don't read it as evidence that compounding is safe.

**Where it does NOT apply:**
- wf is a structured multi-phase process with a repro red→green, tests, validation and two human
  gates. The paper's PRs are mostly one-shot delegations with unknown process, so it says nothing
  about whether wf's phases, critic or repro gate add value.
- There is no correctness or behavioural measure, so nothing here bears on validate, before/after
  measurements or screenshots.
- There is no SvelteKit/Svelte template analysis and no MongoDB-specific injection class. Python is
  covered only by regex smells.
- RQ5's review findings are about GitHub reviewer behaviour in open source (latency to first review,
  bots), not a single owner reading every diff. Only the general "attention is the bottleneck" point
  transfers.
